# Where the 191k went — cost diagnosis

Date: 2026-09-17. Read-only audit; no code was changed.

## The session, found

The 191k is real and I found the exact session that produced it.

- Conversation store: `%APPDATA%\magic-pointer\history\conversations.json`, entry
  `c1789568229834`, title `本会话总是允许`, first turn's question is the paper task
  ("帮我找一篇论文…通讯作者是An Bo…ECCV26…星露谷和computer use…并fetch到本地").
- Agent session log: `data/runtime/agent-sessions/agent-studio-new-8c371b66ae2b49a2ac8a12e54dab47ff.jsonl`
  (787 KB, 176 records).
- Wall clock: 2026-09-16 22:17:09 → 22:26:12. Workspace root
  `C:\Users\zjz65\AppData\Local\Temp\mp-ws-test`.
- Model: `mimo-v2.5` via `https://opencode.ai/zen/go/v1` (`secrets/model.txt`,
  `secrets/openai_base_url.txt`), backend reported as
  `magic_pointer.messages_multiturn_streaming`.

Everything below is decomposition of **real recorded numbers**, not theory. The
only estimates are the split *within* the per-request fixed floor (system prompt
vs. tool schemas), which I measured with the repo's own estimator and
cross-checked against a regression over the 26 real requests.

### The shape of the bill (measured)

| Quantity | Value |
|---|---|
| User turns | 6 |
| Model requests | 26 |
| Total prompt tokens | **376,724** |
| Total completion tokens | **3,426** |
| **Grand total** | **380,150** |
| Largest *single* request context | **23,244 tokens** |
| The 191k turn | turn 6 = **191,499** (190,015 prompt + 1,484 completion) over **10** requests |

The single most important number here is 23,244. **The context never got big.**
The 191k is not one enormous prompt — it is ten sequential re-sends of a
15k–23k context inside one user turn. Turn 6's own context only grew from 15,023
to 23,244 tokens across its ten steps.

### Accounting (measured regression + repo estimator)

Fitting `prompt_tokens` against `messageCount` over all 26 real requests:

```
slope     = 150.6 tokens per message
intercept = 7,967 tokens   (the per-request floor)
R²        = 0.8118   (n = 26)
```

So every request pays a fixed **7,967-token floor** before a single message of
history is counted:

| Bucket | Tokens | Share |
|---|---|---|
| Fixed floor, re-sent 26× (`26 × 7,967`) | ~207,100 | **54.5%** |
| History, re-sent and growing (`150.6 × 1,126 msg-instances`) | ~169,600 | **44.6%** |
| Model output | 3,426 | 0.9% |

**99.1% of the bill is input; 0.9% is anything the model actually wrote.** And
100% of the input is bytes that had already been sent at least once.

Splitting that floor using the repo's estimator
(`app/agent_runtime/token_estimate.py`, run on the actual recorded payload):
system prompt = **1,446** tokens, tool schemas = **5,838** tokens (7,284 total,
within 9% of the 7,967 regression intercept — the two methods agree).

## Ranked causes

### 1. Forty-eight tool schemas are sent on every single request, and 43 of them were never called

**Magnitude: ~152,000 tokens ≈ 40% of the bill.** (Estimated: measured
48-schema payload × measured estimator × 26 requests.)

**Confidence: high.** The payload is recorded verbatim.

Evidence:

- Every one of the 26 `model/request` records in the session log carries exactly
  **48 tool schemas**. The first request carries 48; so does the last.
- Measured payload size: the `tools` array is **15,962 characters** of JSON
  (2,182 CJK chars). The system prompt is 1,997 chars.
- The tools actually invoked in the whole session, counted from the 26
  `assistant/message` records: `Bash` 16, `AskUser` 5, `Search` 2, `Fetch` 1,
  `Glob` 1 — **5 distinct tools, 25 calls.** The other 43 schemas were pure
  overhead on all 26 requests.
- Why all 48 go out: `scripts/conversation_bridge.py:1496` sets
  `tool_limit=128`, and `loop._select_tool_schemas_with_dropped`
  (`app/agent_runtime/loop.py:2108-2127`) sends every non-`deferred` registered
  tool up to that limit, truncated at `selected[:params.tool_limit]`. The loop
  *has* a lazy-load design (`deferred=True` specs, the `Tools` capability
  searcher, `find_capability`) — most capabilities just are not marked
  `deferred`, so nothing is actually held back.
- The loop already knows this number: `loop.py:876` computes
  `tool_schema_tokens = estimate_text_tokens(str(tool_schemas))`. It estimates
  the cost and sends it anyway.

This is the largest single lever and it is the one that does not depend on how
the user behaves.

### 2. The full history is re-sent on every round trip, once per model call

**Magnitude: as a mechanism it multiplies everything; the marginal history cost
is ~169,600 tokens ≈ 45% of the bill.**

**Confidence: high.** Confirmed in code and in the recorded message counts.

Evidence — there is no window management on the request path:

```python
# app/agent_runtime/loop.py:1114-1127
if params.session is not None:
    params.session.record_model_request(
        state.messages, tools=tool_schemas, header=params.request_header, step=turn_number,
    )
events: list[ModelTurnEvent] = []
for event in client.stream_turn(
    state.messages,          # <-- the whole accumulated list, every step
    tool_schemas,
    budget_ms=remaining_ms,
    cancel_scope=loop_scope.token,
):
```

`state.messages` is the entire session surface; `record_model_request`
(`app/agent_runtime/session.py:1079-1105`) enforces that what is sent equals the
event-sourced surface, and records `messageCount = len(projected)`. Recorded
counts grow monotonically 1 → 79 across the 26 requests, never dropping. Nothing
between the surface and the wire trims it.

Trimming *does* exist, but it never fired:

- Proactive compaction triggers at `_PROACTIVE_COMPACT_RATIO = 0.8`
  (`loop.py:218`) of `context_budget_tokens`, and `mimo` maps to a 128,000-token
  window (`app/agent_runtime/model_profiles.py:64`), i.e. it would fire at
  **102,400 tokens**.
- The peak context in this session was **23,244 tokens** — 23% of the trigger
  point. Compaction was irrelevant to this bill, in either direction.

### 3. Twenty-six round trips for one task; twelve of them were a permission loop

**Magnitude: turns 2–5 (pure permission negotiation) = 149,624 tokens = 39.4% of
the bill, across 12 of the 26 requests.** Of that, `12 × 7,967 ≈ 95,600` is
re-sent fixed floor and `12 × 5,838 ≈ 70,000` is re-sent tool schemas alone.

**Confidence: high** — and the root cause was already fixed, 52 minutes *after*
this session ran.

Evidence:

- The five `AskUser` calls in this session, and the turn boundary each one
  creates. `app/agent_runtime/loop.py:1563-1571`: *"A clarification request is a
  turn boundary, not one more tool in a speculative batch"* —
  `_tool_suspends_for_user_input` (`loop.py:1573`) ends the turn, so the user's
  answer arrives as a **new user turn** that re-sends everything.
- The transcript shows the loop exactly: the same `curl` blocked, re-asked, and
  approved five turns in a row. Turn 1 answers "需要下载这篇论文的 PDF…要执行 curl
  命令。可以吗？"; the user grants; turn 2 asks again for `curl`; turn 3 for
  `curl -L`; turn 4 for `powershell`; turn 5 for `powershell` again. Every
  "本会话总是允许" was a full user turn with 3–4 model calls behind it.
- This is `a114543` — *"fix(studio): the permission gate never reached the
  runtime, so it looped forever"*, committed **2026-09-16 23:18:08**, i.e. 52
  minutes after this session ended. Its message names the same evidence: *"the
  same `curl` was blocked, re-asked, and answered five turns in a row, and the
  option label was stored as a user question each time."* Root cause was
  `loop_answer.terminal_to_answer` dropping `kind`/`tool` from `pendingInput`,
  so Studio never rendered the permission card and the generic clarification
  path submitted the option *label* as an ordinary message.

So this specific 191k is a bug artifact. But note what the bug multiplied: it
did not create cost on its own, it converted one task into six turns × the
per-request floor. The floor is still there.

### 4. Prompt caching is not requested, so every re-send is billed at full price

**Magnitude: multiplies causes 1 and 2. The stable prefix — a ~8k floor plus a
slowly-growing history — is what a cache would have covered. I cannot put an
exact token number on the saving without the gateway's price sheet; as an upper
bound, a fully cache-hit prefix bills at a small fraction of fresh input, so the
recoverable share of this bill is large (order of half). Confidence on "caching
is off": high. Confidence on the exact saving: low-medium, see below.**

Evidence:

- `prompt_cache_enabled()` defaults **on**: `model_client.py:1066-1070` reads
  `MAGIC_POINTER_PROMPT_CACHE` with default `"1"`. No such variable is set
  anywhere in the repo, in `secrets/`, or in the launch scripts (grep found no
  assignment).
- The cache breakpoints exist only inside the `api_mode == "messages"` branch:
  `model_client.py:1111-1136` attaches `cache_control: ephemeral` to the system
  block, the last tool, and the last stable history entry. The chat-completions
  fall-through (`model_client.py:1139-1152`) has no cache handling at all.
- The recorded request header says it directly, on **all 26 requests**:
  `"promptCache": false` (field produced at `app/harness/builtin_bundle.py:630-632`
  from `client.prompt_cache_requested`).
- Why false: `AiClientMessagesBackend.prompt_cache_requested`
  (`model_client.py:734-738`) is
  `prompt_cache_enabled() and get_ai_api_mode(base_url) == "messages"`. The
  configured base URL is `https://opencode.ai/zen/go/v1`, which contains no
  `/anthropic`; there is no `model_api_mode.txt` in either secrets directory; so
  `get_ai_api_mode` (`app/ai_client.py:161-176`) returns **`chat-completions`**.
  The conjunction is false.
- Independently: the provider reported no cache fields at all. Across all 26
  `usage` blocks the only keys ever present are
  `{prompt_tokens, completion_tokens, total_tokens}` — no
  `cache_read_input_tokens`, no `prompt_cache_hit_tokens`, no
  `cache_creation_input_tokens`. The aggregation code
  (`loop.py:2202-2210`) is written to pass those through *when a provider
  reports them*; nothing reported them. Whether the gateway caches
  server-side and simply doesn't tell us, I cannot determine from here (see
  below).

Honest caveat on magnitude: for a chat-completions / OpenAI-compatible gateway,
prefix caching is normally automatic and server-side rather than breakpoint-driven,
in which case requesting it is not the lever and the billing question is whether
the provider honoured it. **What I can state is that this client made no cache
request, and no cache hit was reported or recorded for any of the 26 calls.** I
cannot state the price ratio, because the gateway is a third-party relay
(`opencode.ai/zen`) and I have no access to its billing semantics.

### 5. The system prompt: 1,997 chars, ~1,446 tokens, every request

**Magnitude: ~37,600 tokens ≈ 10% of the bill.** (Estimated: measured string ×
repo estimator × 26 requests.)

**Confidence: high on size, high on share.**

The full string is recorded in each request header. It is 1,997 characters
(1,113 CJK), assembled by `SystemPromptBuilder` (`app/agent_runtime/system_prompt.py`)
from sections: Identity, Voice, System (9 numbered rules), Permissions,
Environment, Coding, Deliver, Language, Effort. In the log I read it directly —
it is the sectioned prompt, not a bloated one. This is a modest cost and not
where the fix is.

Worth noting it is *stable within a session* (the date and workspace root are
constant), so it is cacheable — it is part of the prefix that cause 4 fails to
cache, not a source of instability.

### 6. The verification gate adds one forced request per write-then-finish turn

**Magnitude: ~23,000 tokens ≈ 6% of the bill in this session (one extra request
at turn 6's step-10 context size).** **Confidence: medium** — the injection is
certain, the attribution of exactly one step to it is inferred from the artifact
plus the code path.

`app/agent_runtime/turn_verification.py:26-30` defines `_NUDGE_MESSAGE`; when the
model has performed a gated write and has no fresh verification evidence, the
loop injects it as a user message and **refuses the first completion attempt**
(`should_nudge_before_completion`). The injected message is in the log verbatim
(111 chars, `origin: instruction`, the only injected user message in the
session) — and it is a full extra model round at the then-current context size.

## Ruled out

These were plausible and are not what happened — recording them so nobody
re-walks them.

- **A huge context / unbounded history growth.** No. Peak single request was
  23,244 tokens. The history at the *end* of the session was ~15k tokens of
  messages. There is nothing "unbounded" about it; the cost is repetition, not
  size. The 128k window and the 80%-of-budget compaction threshold were never
  approached.
- **Tool results blowing up the context.** No — not in this session. The largest
  single-step prompt increase was **+2,852 tokens** (turn 6, step 6→7, the PDF
  read). The caps never bound: `_MAX_TOOL_RESULT_CHARS = 64_000` (`loop.py:317`),
  `_MAX_TURN_TOOL_RESULT_CHARS = 120_000` per round (`loop.py:2876`),
  `_MAX_READ_CHARS = 50_000` / `_MAX_READ_LINES = 2_000` (`coding_tools.py:32-33`),
  `_MAX_OUTPUT_CHARS = 64_000` for Bash stdout tail (`coding_tools.py:34,1531`).
  These caps are large enough to be a real latent risk on a different task (a
  single `Read` at the cap is ~12k tokens; a four-call round can legally enter
  120,000 chars ≈ 30k+ tokens, ~120k if CJK) — but they did **not** produce this
  bill.
- **Retries resending the full context.** No retries occurred. All 26 responses
  have `outcome: "completed"`; steps are contiguous `1..N` within each turn
  (4+3+2+4+3+10 = 26) with no gaps and no repeats. The retry machinery exists
  (`LoopModelClient` `max_provider_retries=2`, `model_client.py:224`; the
  truncated-turn escalation at `loop.py:1309-1315`) but never fired here.
- **The `outputTokens`-only data-loss point in the conversation bridge.** Already
  fixed in the working tree. `git show a114543` / `git diff` on
  `scripts/conversation_bridge.py` shows the five-field loop
  (`inputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `outputTokens`,
  `reasoningTokens`) present at ~`scripts/conversation_bridge.py:437-455` in the
  uncommitted working tree. The brief's "confirmed data-loss point" describes
  HEAD, not the current file. It was a reporting bug regardless, and reporting
  bugs do not produce a bill.

## What I could not determine

- **The gateway's cache and price semantics.** `opencode.ai/zen/go/v1` is a
  relay. I can prove the client sent no cache breakpoints and that no cache-read
  tokens were reported. I cannot prove whether the upstream provider (mimo-v2.5)
  caches prefixes automatically, nor what a cached vs. fresh input token costs
  there. So the *rank* of cause 4 is certain and its *token magnitude* is not.
- **Whether the 48-schema list is stable across sessions.** Within this session
  it was constant at 48 on every request. I did not verify whether the
  `registry.list()` order or membership varies per session, so I cannot say
  whether an enabled cache would have been invalidated by tool-list churn. This
  matters for cause 4 and nobody has measured it.
- **The exact per-request split of the 7,967-token floor.** 5,838 tools + 1,446
  system = 7,284 from the repo estimator, vs. 7,967 measured by regression. 9%
  apart. The residual ~680 tokens is unexplained and is probably estimator error
  on this provider's tokenizer, but I did not isolate it.
- **Whether other sessions are similar.** I decomposed the one session that
  produced the 191k. The conversation store holds 20 conversations; I did not
  audit the rest, so I cannot say whether 26-requests-per-task is typical or
  whether this was an outlier produced by the (now fixed) permission bug.

---

## The one-line answer to "what is the agent wasting"

For this session, ranked by tokens: **40% is 48 tool schemas re-sent 26 times,
39% is five permission round trips that a since-fixed bug turned into five extra
user turns, ~10% is the system prompt re-sent 26 times, ~45% is history re-sent
26 times** (these overlap — the first, third and fourth are all "the same prefix,
paid for again"), and **0.9% is anything the model wrote**. Fixing the permission
loop removes this instance; the per-request floor and the absence of caching are
what remain, and they are what make the *next* 191k possible.
