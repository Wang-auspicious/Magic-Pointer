# Vida 界面规格书

> 用途：给「照着做」的实现者一份不需要再看视频、也不需要猜的规格。所有数字来自对
> `参考/Vida/*.mp4`（1920×1080 @ 60fps，5 段）与 `参考/Vida实机体验/*.png`
> （Windows 11，3120×2080 与 2800×1600）的逐帧像素测量，测量脚本 `.tmp/vida/measure.py`。
>
> **证据分级**：**实测**＝脚本量出的像素/毫秒；**读图**＝放大帧目视确认的结构；
> **推断**＝由前两者推出的实现方式，标注理由。未标注的一律是实测。
>
> 只写「是什么」和「多少」。为什么这么设计、我们抄哪些，见 [`Vida.md`](../../Vida.md)。

## 0. 先读这一节：最容易做错的七件事

按复刻失败的严重程度排序。这七条做错，其余做对也不像。

1. **有两套卡，不是一套。** 深色卡＝Vida 主动开口问你（Proactive），浅色卡＝任务做完了给你看回执（Receipt）。背景色一个 `#000000` 一个 `#F9F8FB`，按钮一个是等宽平分的药丸、一个是右对齐的小方角按钮。§3 与 §4。
2. **产物写进目标应用的输入框，不是剪贴板。** ReplyRescue 最后一帧，草稿整段落在 Slack 的 `Message #design` 里，placeholder 还在下面。做成「已复制」就丢掉了这个产品的核心。§7.1。
3. **进度不用百分比、不用转圈。** 用一条从左到右扫过的柔和彩虹色带（蓝→绿→粉），配文字 `Generating …`。§6.2。
4. **证据流是主要输出，不是折叠的 thinking。** `✓` 行是「我做了什么」，`→` 行是「我从那个动作里读到什么」，用等宽灰字与黑色正文分离。§5.3。
5. **追问框绑当前前台页面。** placeholder 逐字是 `Ask Vida anything about this page…`，切窗口就该变。§5.4。
6. **PromptRescue 的“三张卡”是三个串行语义阶段，不是三张并排 UI。** 第一张把已有项目记忆摊开，第二张重新核验当前来源，第三张才把可交付 prompt 交给用户批准。第一、二张复用同一个右侧面板，中间会清空换页；第三张切换为居中回执。§7.4。
7. **唤起浮层前必须冻结写回目标。** 浮层一出现就夺走焦点；如果没有先保存原前台窗口、编辑框和页面身份，批准后只能猜该写到哪里。PromptRescue 的终点是 Claude 输入框，ResumeRescue 的终点是 PDF 文件。§7.4.6。

## 1. 坐标系与换算

全部测量在 **1920×1080** 画布上完成。移植到别的分辨率时按下式换算，四舍五入到整数像素：

```
scale = min(屏幕宽 / 1920, 屏幕高 / 1080)
实际值 = round(规格值 × scale)
```

Windows 实机截图是 3120×2080（缩放 200%）与 2800×1600。本文所有 Windows 侧的数字都已
除以对应缩放，折算回 1× 逻辑像素，与 macOS 侧同一坐标系，可直接比较。

是半透明 + 背景模糊。**推断**：`background: rgba(255,255,255,0.88)` 叠
`backdrop-filter: blur(30px) saturate(1.2)`。理由：卡内不同位置的采样值随其后方背景明暗

说明模糊半径足够大、不透明度足够高。

## 3. 常驻入口

### 3.1 macOS：菜单栏胶囊

贴屏幕顶边、覆盖在系统菜单栏之上的黑色药丸。

| 属性 | 值 |
|---|---|
| 高度 | **29px**（y=0…28，y=29 起为背景） |
| 顶边距 | **0**（紧贴屏幕顶端） |
| 右缘 x | **1131**（固定） |
| 宽度 | 随状态变化，见下表 |
| 生长方向 | **向左**（右缘钉死，左缘外扩） |

宽度实测：

| 状态 | 宽度 | 左缘 x | 量自 |
|---|---|---|---|
| 空闲 | **299px** | 833 | DailyWrap 1.0s / 5.0s |
| Processing | **320px** | 812 | DailyWrap 8.5s / 16.0s / 25.0s |
| 长文案 | **362px** | 790 | DailyWrap 13.0s |

内容：左端一个旋转加载圆环，右侧文案（如 `Processing...`）。

**实现要点**：宽度必须动画过渡而不是跳变，且 `transform-origin` 在右端。
**推断** `transition: width 260ms cubic-bezier(0.32, 0.72, 0, 1)`——理由见 §6.1 的缓动说明。

## 4. 卡片 A：浅色任务回执卡（Receipt Card）

任务**做完之后**出现，给用户看结果并要一次确认。这里量到的 404×333 是
`outputKind=file-plan` 的文件整理实例，不是所有回执卡的固定尺寸；文本 prompt、写回草稿、
PDF 文件各有不同内容适配器，见 §4.4。

### 4.1 几何（实测，WorkspaceCleanup 12.8s，未被镜头推近的原生帧）

```
画布 1920×1080
┌──────────────────────────────────────────────────────┐
│                                                      │
│                                    x=1322 ─┐         │
│                              y=296 ────────┼───────┐ │
│                                            │ 卡片  │ │
│                                            │404×333│ │
│                              y=628 ────────┼───────┘ │
│                                    x=1725 ─┘         │
│                                                      │
└──────────────────────────────────────────────────────┘
距右边缘 195px    距底边缘 452px
```

| 属性 | 值 |
|---|---|
| 尺寸 | **404 × 333 px** |
| 左上角 | (1322, 296) |
| 右下角 | (1725, 628) |
| 距屏幕右缘 | 195px |
| 距屏幕底缘 | 452px |
| 圆角 | 8px |
| 背景 | `--card-bg-light`，半透明 + backdrop blur |
| 阴影 | 柔和大范围投影（读图；**推断** `0 12px 40px rgba(0,0,0,0.18)`） |

### 4.2 内部纵向布局（实测，y 相对卡片顶边）

逐行统计卡内暗像素得到的元素行段：

| y 范围 | 高 | 内容 |

| **97–105** | 9 | 正文第 2 行 |
| **110–117** | 8 | 正文第 3 行 |
| **124–235** | 112 | 预览区（内嵌容器 + 三个文件夹图标 + 文件名） |

| **295–332** | 38 | 底部操作栏（左重跑图标，右 Reject/Approve） |

推出的间距体系：

### 4.3 元素细节（读图）

**meta 行**：Vida logo（约 12×12）+ 8px 间隙 + `TASK FINISHED`，等宽、大写、**字距明显加宽**
（约 0.12em），颜色 `--text-meta-light`，字号约 9px。

**预览区**：内嵌一个比卡片略深的圆角容器，内部三个文件夹图标横排等距，图标下方是文件名
标签（`Map Apps` / `DietControl AI` / `Apple Products`）。

> 这是全套设计里最值得抄的一处：**预览渲染成结果本来的样子**（真的画文件夹），
> 不是回显一行命令。用户 0.3 秒就能判断该不该批准。
> 按产物类型分派渲染：文件操作画目录树/文件夹、文本改写画 diff、写回画输入框前后对照。

**单选行**：`Approve` 选中态为实心绿点 `--accent-green-soft`，`Reject` 为空心灰圈。
注意这一行与底部按钮**语义重复**，是 Vida 的冗余设计，复刻时可保留也可只留底栏。

**底部操作栏**：
- 左侧：环形箭头「重跑」图标，无文字
- 右侧：`Reject`（描边、透明底、深灰字）+ 8px 间隙 + `Approve`（`--btn-primary-bg` 实心、白字）
- 按钮高度约 26px，横向内边距约 14px

### 4.4 回执卡不是一个固定模板，而是一个壳 + 产物适配器

逐帧对比三个视频后可以确认，`TASK FINISHED` 只是统一外壳：

| `outputKind` | 视频 | 中间主体 | 卡片形态 | 批准后的动作 |
|---|---|---|---|---|
| `file-plan` | WorkspaceCleanup | 三个文件夹图标 + 文件名 + Approve/Reject 单选 | 404×333，偏竖 | 真正建目录并移动文件 |
| `text-writeback` | ReplyRescue | 将要写回 Slack 的完整草稿 | 宽卡，随文本自适应高度 | 写入 Slack 输入框 |
| `prompt-writeback` | PromptRescue | 将要写入 Claude 的完整 prompt | **横向宽卡**，无文件预览、无单选行 | 写入 Claude 输入框并在演示中发送 |
| `file-artifact` | ResumeRescue | PDF 图标、文件名、保存路径、打开文件/所在目录 | 不另弹居中卡，嵌在流式面板 | 打开生成的简历 PDF |

因此实现上应是：

```text
ReceiptShell
├── MetaRow(VidaLogo, "TASK FINISHED")
├── ArtifactRenderer(outputKind, artifact)
└── ActionBar(rerun, reject, approve)
```

禁止把 `404×333` 写死到 `ReceiptShell`。它只属于文件夹预览这一种 renderer。PromptRescue
21.5s 的 prompt 卡宽高比约为文件整理卡的两倍以上；即使考虑视频运镜，二者也不可能是同一固定尺寸。

## 5. 卡片 B：右侧流式面板（Stream Panel）

任务**进行中与刚结束**时的主界面。DailyWrap 20.0s 是最完整的一帧。

### 5.1 位置与尺寸

贴屏幕右缘的竖长面板，圆角，半透明毛玻璃（背后山景清晰可辨）。

原生比例帧中该面板未完整出现，故不给绝对像素，改给比例（**推断**，由推近帧反算）：

| 属性 | 值 |
|---|---|
| 宽度 | 约屏宽的 30%（1920 下约 560–600px） |
| 距右缘 | 约 24px |
| 垂直 | 上下各留约 60px，其余撑满 |

### 5.2 结构（自上而下，读图）

```
┌─────────────────────────────────────────────┐
│ Work Progress Summary        ⊞   ↺   ✕      │  ← 标题行
├─────────────────────────────────────────────┤
│ ✓ Align with engineering on revised QA timing│
│                                             │  ← 证据流
│ ✓ Cross-checking Friday launch readiness    │
│ ✓ Prepare design handoff by Thursday PM     │
│                                             │
│ The onboarding redesign is progressing, but │  ← 结论正文
│ the timeline is at risk due to added scope  │
│ and unresolved dependencies.                │
│                                             │
│ ┌───────────────┐                           │
│ │ [日报缩略图]   │                           │  ← 产物缩略卡
│ │  可点开       │                           │
│ └───────────────┘                           │
├─────────────────────────────────────────────┤
│ ⊙ Vida has completed your task.             │  ← 完成行（绿）
├─────────────────────────────────────────────┤
│ Ask Vida anything about this page...        │  ← 追问框
│ 📎                              🎤    ↑     │
└─────────────────────────────────────────────┘
```

标题行右侧三个图标依次为：另存/归档、历史、关闭。

### 5.3 证据流的两种行（这是信任的来源）

| 前缀 | 语义 | 排版 |
|---|---|---|
| `✓` | **动作**：我做了什么 | 黑色正文、无衬线 |
| `→` | **事实**：我从那个动作里读到什么 | **等宽、灰色** |

ReplyRescue 中可见的实例：

```
✓ Reviewed latest Figma onboarding flows
  → 12/16 screens finalized
  → Mobile handoff still pending
✓ Cross-checking Friday launch readiness
  → Design likely finishes Thursday
  → Engineering QA window is tight
```

**版式即语义**：等宽灰＝我读到的原文，黑色正文＝我的结论。等待的十几秒因此在建立信任，
而不是在耗尽耐心。这条比任何 loading 动画都值钱。

### 5.4 追问框

placeholder 逐字为 `Ask Vida anything about this page...`——**绑定当前前台页面**，
切换窗口时 placeholder 应随之改变。用户因此不必交代背景。

底部左侧回形针（附件），右侧麦克风 + 圆形上箭头提交键。

### 5.5 同一个右侧面板内允许“整页换卡”

PromptRescue 证明右侧流式面板不是一份内容从头追加到底。它会保留标题栏和底部追问框，
只替换中间 body：

```text
项目记忆卡（15.98–17.40s）
  ↓ body 清空（17.75s）
现场核验卡（18.25–20.00s）
```

换卡时先把旧 body 淡出/清空，再让新标题和证据逐项长出；不要把两份内容硬接成一张长滚动页。
用户因此能读出“这是我原来知道的”与“这是我刚刚重新查证的”两层可信度。

## 6. 卡片 C：深色主动提议卡（Proactive Card）

**Vida 主动开口**时用。这是 §0 第 1 条说的另一套卡，与 §4 的浅色回执卡完全不同。
量自 DailyWrap 11.5s。

### 6.1 结构

```
┌───────────────────────────────────────────────┐
│ ♥                                    ⌃    ↗   │  ← logo + 折叠 + 外链
│                                               │
│  Workflow summarization:                      │  ← 标题，白色粗体
│                                               │
│  ┌─────────────────────────────────────────┐  │
│  │ Want Vida to summarize what you got     │  │  ← 内嵌框 #191919
│  │ done today?                             │  │     文字 #929292
│  └─────────────────────────────────────────┘  │
│                                               │
│  ┌──────────────────┐ ┌──────────────────┐   │
│  │      Deny        │ │     Approve      │   │  ← 等宽平分的药丸
│  │    (#191919)     │ │    (#2FDB5F)     │   │
│  └──────────────────┘ └──────────────────┘   │
└───────────────────────────────────────────────┘
```

| 属性 | 值 |
|---|---|
| 背景 | `#000000` |
| 内嵌框 | `#191919` |
| Deny 底色 | `#191919`，白字 |
| Approve 底色 | `#2FDB5F`，白字 |
| 两按钮 | **等宽平分**，中间约 16px 间隙，全圆角药丸 |
| 卡圆角 | 约 28px |

标题末尾的冒号（`Workflow summarization:`）是它的固定写法——提议卡的标题是「事由：」，
下面那句才是问句。

### 6.2 进度表现：彩虹扫过

任务运行中，输入胶囊内呈现一条**从左到右**的柔和渐变色带，配文字 `Generating …`，
右端提交键变为**黑色圆形停止键**（圆内一个圆角方块）。

渐变色序（读图，ReplyRescue 6.8s）：淡蓝 → 淡绿 → 淡粉，低饱和、高明度，像一层薄雾扫过，
**不是**高饱和的彩虹。

**推断实现**：
```css
background: linear-gradient(90deg,
  transparent 0%, #BBD8F5 25%, #B6E5C4 50%, #F2C2D2 75%, transparent 100%);
background-size: 200% 100%;
animation: sweep 1600ms linear infinite;
@keyframes sweep { from { background-position: 200% 0 } to { background-position: -100% 0 } }
```
理由：单帧中色带占胶囊约一半宽度且两端淡出，说明渐变尺寸约为容器两倍并循环平移。

### 6.3 缓动曲线

全套动效未见任何弹跳或回弹，起步快、收尾长，是典型的「减速进入」。
**推断**统一使用 `cubic-bezier(0.32, 0.72, 0, 1)`（Vercel/Linear 一系常用值），
理由：进入动画的覆盖率曲线（§7.2）前段斜率大、后段平缓且无过冲。

### 7.4 PromptRescue：三张逻辑卡与完整状态机

#### 7.4.1 一句话结论

用户在 Claude 里只说了极度欠定的 `Give me a prompt.`，Vida 仍知道 prompt 是为
**DietControl AI 落地页**准备的。原因不是它多看了一屏，而是它在用户开口前已经把 Gmail
任务、Notion 路线图、Google Docs 产品要求和既有项目记忆连成了一个对象；随后又对关键来源做
了一轮新鲜度核验，最后才生成可批准、可写回的 prompt。

```text
Gmail 紧急需求
  ├── DietControl AI Product Roadmap（Notion）
  └── UX and Product Requirement（Google Docs）
         ↓ 同一实体：DietControl AI
Claude 当前输入目标 + "Give me a prompt."
         ↓
卡 1：已有项目记忆（我原来知道什么）
         ↓ 清空换页
卡 2：现场来源核验（我刚刚确认了什么）
         ↓
卡 3：可审批 prompt（我准备写什么）
         ↓ Approve
Claude 输入框 → 发送 → Claude 生成真实 HTML 预览
```

这里最重要的不是 prompt 文案，而是**对象连续性**：用户从 Gmail 切到 Notion、Google Docs、
再切到 Claude，`DietControl AI` 这个项目对象没有丢。只把 Claude 当前一屏送给模型，绝不可能
从 `Give me a prompt.` 推出后面的完整需求。

#### 7.4.3 卡 1：已有项目记忆（Project Memory）

这张卡回答“Vida 在用户开口前已经知道什么”。标题栏是 `DietControl landing page update`，
body 里不是三句随便的摘要，而是三个工作流组；每组都有一条黑色主任务和两条浅灰等宽事实：

```text
• Explore user feedback on Diet Control app iterations
  Collected insights from 5 user testing sessions
  Compile features for the next design sprint

• Benchmark against top AI diet apps
  Analyzed design styles from 8 leading competitors
  Documented key differentiators and user experience

• Collaborate with marketing on product positioning
  Drafted initial messaging framework and value propositions
  Set up a meeting to align on branding elements
```

它的职责不是声称“刚刚读取成功”，而是把**长期/先前压缩出的项目状态**摊给用户看。
因此它没有 `✓`，使用圆点分组；浅灰等宽行是记忆里的事实，黑色行是工作流主题。

#### 7.4.4 卡 2：现场核验（Fresh Verification）

body 清空后换成 `Investigating project status`。这次每条都有 `✓`，且严格采用三段式：

```text
✓ Reviewed latest Slack messages
  → User feedback on design is positive
  → Need to address concerns about the color scheme

✓ Checked Notion doc
  → Outlined key features and target user feedback
  → Need to refine the user flow section

✓ Reviewed Google doc
  → Updated product roadmap and key features
  → Need to add more details on the revenue model
```

末尾结论：

> DietControl landing page design is progressing well, with positive user feedback and a clear product roadmap.

这张卡的语法可以直接固化成数据结构：

```text
EvidenceStep {
  sourceRef,       // 可下钻的真实来源，不只是 "Google doc"
  action,          // Reviewed / Checked
  observedFact,    // 来源里实际读到的事实
  implication,     // 对当前交付意味着什么/还缺什么
  capturedAt,
  contentHash
}
```

**演示自身有一处一致性错误**：前面画面明确展示的是 Gmail 邮件，但核验卡第一条写成了
`Slack messages`。这不能照抄成产品行为。实现必须让 `sourceRef.app` 驱动展示文案；读的是 Gmail
就显示 Gmail，绝不能让模型凭印象生成来源名。来源名与证据哈希要来自捕获层，不来自最终文案模型。

#### 7.4.5 卡 3：可审批 prompt（Delivery Receipt）

第三张卡不再占右侧栏，而是居中横向铺开。它只展示**将要写入 Claude 的最终文本**，不再混入
记忆摘要、检索日志或内部推理：

> Craft a compelling landing page for DietControl AI, the AI-driven nutrition app. Highlight key features,
> user benefits, and social proof. Use a clean, modern design with a health-focused color scheme. Optimize
> for mobile and include a clear call to action to book a demo.

底栏左侧重跑，右侧 Reject / Approve。点击 Approve 后，视频显示这段文本先完整进入 Claude
composer，再成为已发送消息，最后拿到真实 HTML 预览。故交付完成条件不是“prompt 已生成”，而是：

```text
drafted → user_approved → target_reacquired → written → submitted → downstream_result_visible
```

前三态属于 Vida；`downstream_result_visible` 是对整条链的演示级验证。产品实现至少要做到
`written` 后读回校验，不能把一次模拟按键当作成功。

#### 7.4.6 写回目标算法：浮层出现前冻结，批准后重获并校验

PromptRescue 对实现最硬的要求是：**用户唤起 Vida 时，原本的 Claude 输入框会失去焦点。**
所以目标不能等 Approve 时再找；必须在浮层抢焦点之前创建一张短期 `TargetLease`：

```text
TargetLease {
  capturedAt,
  hwnd,
  pid,
  processName,
  windowTitle,
  documentUrl,
  elementRuntimeId,
  elementRole,
  elementBounds,
  editableUnderPointer,
  contentFingerprint
}
```

目标候选优先级（从高到低）：

1. 用户明确圈定/点名的编辑区；
2. 唤起前已经聚焦的可编辑元素；
3. **鼠标正悬停的可编辑元素**（即使用户没点击），但必须属于当前前台窗口；
4. 当前前台应用唯一且高置信的主 composer（DOM/UIA/Office 适配器识别）；
5. 没有高置信目标：只生成回执，不自动写，要求用户重新指向。

提交过程必须是：

```text
onWake:
  lease = captureTargetBeforeOverlayFocus()

onApprove:
  candidate = reacquire(lease)
  assert same process/window/document
  assert editable role + bounds/fingerprint still compatible
  focus(candidate)
  write(text)
  readBackAndCompare(text)
  if deliveryPolicy == "submit": submit()
```

平台适配顺序：浏览器/Electron 优先 DOM 或 DevTools；Office 优先 COM；普通应用用 UIA；终端用终端
控件/受控粘贴。**终端默认只粘贴、不自动回车**，因为回车等于执行命令；只有用户在回执里明确批准
“写入并执行”时才发送 Enter。聊天 composer 可以在批准后自动发送，但要把 `write` 与 `submit`
记录成两个独立状态，方便失败恢复。

这套 lease 同时解决用户描述的两个场景：鼠标放在未点击的输入框上仍可识别；浮层夺焦点后仍能回到
原来的 Claude/终端，而不是把文字打进 Vida 自己的输入框或后来切到的另一个窗口。

#### 7.4.7 复刻用状态机

```text
IDLE
  → COMPOSING                 底部白胶囊
  → GENERATING               彩虹色带 + Stop
  → SHOW_PROJECT_MEMORY       右侧卡 1
  → REFRESHING               body 清空，shell 保留
  → SHOW_FRESH_EVIDENCE       右侧卡 2
  → VERIFIED                 绿色完成行
  → SHOW_DELIVERY_RECEIPT     居中卡 3
  ├── REJECTED               返回 COMPOSING，保留草稿
  ├── RERUNNING              回 GENERATING，沿用同一 ContextBundle
  └── APPROVED
        → REACQUIRE_TARGET
        → WRITING
        → WRITTEN_VERIFIED
        → SUBMITTING（按目标策略）
        → DELIVERED
```

不要把它实现成 `loading -> result` 两态。三张卡分别承担“记忆透明”“新鲜度透明”“动作可控”，
少一层都会退回用户说的那种“只看一屏、凭局部猜答案”。

### 7.5 ResumeRescue：原规格漏掉的完整链路

ResumeRescue 与 PromptRescue 共用同一条底层逻辑，但产物不是写回文字，而是一个文件：

| 时刻 | 事件 | 可见证据 |
|---|---|---|
| 0.0–1.0s | 打开旧简历 | 左侧表格型 `RESUME`，包含履历、技能、奖项 |
| 1.5–4.5s | 打开 LinkedIn | `Alex Morgan` 个人资料页，补充公开职业身份 |
| 5.0–8.5s | 打开 Google Docs | `Experiences` / `Market Research`，补充最近项目与量化成果 |
| 9.0–12.0s | 用户指令 | `I need to update my resume to apply for the senior level position` |
| 13.5–14.5s | 深色提议卡 | `Improve the current resume?`，明确“已看旧简历、LinkedIn、最近成就与职业里程碑” |
| ~14.5s | Approve | 用户批准使用这些跨应用材料改简历 |
| 15.5s | 流式面板 | 用户原话置顶；状态为 `REVIEWING` |
| 17.0–19.0s | 证据流 | `Read through old resume (ver. 3.2)`、`Reviewed project milestones and...`、`Review LinkedIn page "Alex Morgan"` 逐项出现 |
| 20.5s | 结论 | `I have reviewed the resume, LinkedIn page, and project milestones.` |
| 21.0s | 文件产物 | PDF 行出现，带文件名、保存路径、打开目录与打开文件按钮；绿色完成行出现 |
| 23.5s | 真结果 | 新简历在独立窗口打开，旧简历仍在背后，可直接做前后对照 |

深色提议卡原文：

```text
Improve the current resume?
I've reviewed your previous resume and LinkedIn profile, and your most recent
achievements and career milestones.
[Deny] [Approve]
```

这个视频补齐了两个实现要求：

1. **主动提议必须说清它准备用哪些上下文。** 不能只问“要不要优化简历”，要明确旧简历、LinkedIn、
   最近成果都已准备好，让用户知道批准的范围。
2. **文件型产物留在流式面板内。** PDF 行同时提供保存路径、打开文件、打开所在目录，完成后还把真文件
   打开给用户看；它不需要再套一张巨大的 `TASK FINISHED` 文本卡。

演示也有一处不能照抄的错误：生成的是 Alex Morgan 的新简历，文件行却显示
`Report of New Energy.pdf`。实现中产物名必须由 `artifact.type + subject + purpose` 确定并在落盘前
校验，例如 `Alex_Morgan_Senior_Growth_Resume.pdf`，不能让模型随手沿用别的任务文件名。

### 7.6 DailyWrap：主动层从“通知触发”到“真实回信”

原规格已经量了 DailyWrap 的面板和日报卡，但漏了完整因果链。逐帧补完后，它的逻辑是：

```text
经理通知要今日总结
  → Vida 把这条通知判为“需要交付”的触发器
  → 用户继续正常工作/切窗口
  → Vida 主动提议总结今天完成的工作
  → 用户批准“使用今天的跨应用上下文”
  → 现场复核 Figma / 日历 / Google Docs / Slack 等来源
  → 生成可视化 Share Report
  → 报告回到 Slack 工作流
  → 经理回复确认，闭环
```

| 时刻 | 事件 | 产品意义 |
|---|---|---|
| 0.5–2.0s | 用户在 Notion 看 `Launch Strategy Draft` | 当下工作对象 |
| 2.5–4.5s | Slack 通知：`Can you send me a quick summary of today's progress?`，通知外缘有紫色辉光 | **触发器被 Vida 命中**，但此时不抢输入焦点 |
| 5.0–8.0s | 用户继续浏览文档，随后进入多窗口总览 | 允许用户继续工作；后台已有一天的时间线，而非从通知这一屏临时猜 |
| 10.0–12.5s | 深色提议卡 `Workflow summarization:` / `Want Vida to summarize what you got done today?` | 先提议、后执行；Deny/Approve 等宽 |
| ~12.5s | Approve | 用户批准使用今天积累的上下文做汇总 |
| 13.0–16.5s | 画面依次经过 Figma、日历、Google Docs、终端、Slack | 演示跨应用证据覆盖；右侧面板保持存在 |
| 17.5–18.5s | `Work Progress Summary` / `Investigating project status`，证据项逐条出现 | 新鲜度核验，不直接把旧记忆当真 |
| 19.0–20.0s | 风险结论 + 绿色完成行 + 日报缩略图 | 把证据压成可交付结论，并给出产物入口 |
| 21.0–24.0s | 打开完整 `Share Report` | 环形图、时间分布、Key Deliverables、Tomorrow's Plan、Keywords |
| 24.5–26.5s | 回到 Slack，报告进入消息工作流 | 产物没有困在 Vida 内部 |
| 27.0–28.0s | Daniel Whitman 回复 `Thanks for the clear summary Will. Let's push this forward.` | **外部收件人确认**，才是演示闭环 |

这条链把“主动”拆成两个互不替代的部分：

1. **确定性触发**：通知里出现交付请求，触发候选；这一步不需要 agent 自由发挥。
2. **历史上下文汇总**：从当天时间线里取证，再对关键来源做刷新；只靠通知和当前 Notion 一屏无法生成
   8 小时分布、完成项、明日计划。

实现时通知辉光只能表示“候选已命中”，不能表示“任务已执行”。真正执行必须等深色卡 Approve；
拒绝后同一触发器不应反复出现。

## 10. 测量方法

复现或补测用 `.tmp/vida/measure.py`：

```bash
python .tmp/vida/measure.py grab WorkspaceCleanup.mp4 12.8 out.png   # 取帧
python .tmp/vida/measure.py row  WorkspaceCleanup.mp4 12.8 460       # 横扫边界
python .tmp/vida/measure.py col  WorkspaceCleanup.mp4 12.8 1500      # 纵扫边界
python .tmp/vida/measure.py px   WorkspaceCleanup.mp4 12.8 1700 340  # 取色
```

两个坑：

1. **镜头一直在推拉。** 五段视频都有运镜，大部分帧是放大的，直接量会得到错误尺寸。
   先用「菜单栏暗色比例 ≈ 0.21」筛出原生比例帧再量。已知可用的原生帧：
   WorkspaceCleanup 12.8s、DailyWrap 1.0/5.0/8.5s。
2. **颜色不要单点采样。** 卡片半透明，单点会采到抗锯齿边缘或透出的背景。
   取区域后按亮度分位数取中位数（脚本里的 `region()` 写法）。
