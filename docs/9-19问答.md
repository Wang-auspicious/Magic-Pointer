## A1

我的判断是：你现在首先撞上的不是 CU 的能力上限，而是工程链路还没有形成一个稳定的整体。同一次圈选，在不同模块里被重新解释；读取失败、对象没定位、模型不能看图，又会被不同层用不同方式处理。继续叠加感知模块，很可能变成「支持的情况越来越多，最简单的任务仍然随机失败」。你应该先把「指对对象、交对材料、执行一步、确认结果」这条最短路径做牢，再向复杂任务扩展。

Astra 有一个值得直接借鉴的公开实现方向：OpenAI 现在对它的 computer use 推荐代码执行接口，让模型在常驻环境中用一段代码完成一小组操作，代码里可以包含循环和条件判断，再返回截图检查结果；不是每点一下鼠标，都重新请求一次模型。这能减少模型往返，也是你可以复用的工程思路。但这不等于公开了 Astra 的完整内部实现，更不能从演示里截图出现得少，就认定它很少处理视觉。你提到的「演讲者模式」，我没有找到足以确认其内部机制的官方技术说明。

另一个关键是，它也不是坚持「所有事情都靠看屏幕」。OpenAI 的桌面产品文档明确建议：应用有专用插件或结构化接口时，优先用它们获取数据和执行重复操作，GUI 用于那些必须通过界面完成的部分。MP 应该采用同样的原则：用户通过指针表达意图，但系统不必通过鼠标完成所有工作。指针是入口，不是执行方式的限制。

Google 的官方演示说明，真正有价值的也不是光标动画，而是把「对象、意图、去向」连起来：指着 PDF 生成摘要并放进邮件，指着表格转换成图表，用「这个、那个、这里」连接多个材料；Googlebook 还展示了把照片和标志组合成海报。这些交互值得做，但官方明确标注了实验环境和缩短演示时序，不能据此认定它在任意软件上都稳定、即时完成。

所以，你的产品目标可以更具体：不是「一个能操纵电脑的聊天框」，而是「我指一下，它知道我要处理什么；我再指一下，它知道结果放哪里；整个过程能检查、能纠正」。这比让用户重新描述软件、窗口、文件、段落，天然少一层沟通成本。复杂任务也从这里生长，而不是一开始就让模型自由点击几百步。

眼下最先修的，是与你换什么模型完全无关的错误。你的说明里，回答桥已经允许 8 MiB，快照桥却仍使用 64 KiB 默认上限，还把传输超限翻译成「请缩小选区」。这是产品自己的管道问题，却让用户反复修改手势。应统一整条链路的字节预算和错误协议，大截图、大证据通过受控引用传递，不要反复塞进 JSON；所有失败都必须关联当前请求，不能被过滤后变成沉默超时。

第二个必须收口的是对象身份。现在删掉一笔，相关材料仍可能留下；工具宣称支持 element 锚点，实际解析器却不支持。这会让用户「明明改对了」，模型仍拿错材料或调用必败工具。每一笔从产生开始就应有不变的 ID，材料、来源、引用都绑定这个 ID，不依赖数组位置；删除、重选、纠正必须一起更新。工具也只暴露当前环境真正能完成的能力。

还有一个比报错更危险的地方：你的覆盖判据在「有文字、没有矩形」时，可以直接认为读到了圈选内容。这样，读到整篇文章也可能压掉真正需要的视觉补读。应该区分「读到了这个窗口的内容」和「已经绑定到用户指定对象」。有原生选区、单元格地址、文本范围等明确绑定，可以不依赖几何；只有一段文字，不能算命中。拿不准时保留为上下文，继续定位，不要让错误的成功阻断后续路线。

视觉也应该成为产品自己的可用能力，而不是用户选中纯文本模型之后才突然消失。规划模型和视觉读取可以独立配置，启动时检查实际能力；需要云端补读时明确告知。对于必须看图的步骤，直接由合适的视觉模型处理，不要固定走「视觉模型描述一遍，再让文字模型重新理解一遍」。如果没有可用视觉，就提供重新选取文字、换来源或人工指认，而不是让整个任务报错退出。你目前已经出现过「界面允许提交，最后才发现所选模型不能读图」的情况。

速度上，最值得先砍的是重复工作。现在多笔可能各自跑完整结构化读取，随后各自 OCR，再逐笔串行 Look。建议改成：同一窗口、同一帧尽量只采一次结构和一次 OCR，多笔只是对共享结果分别筛选；确实需要视觉的多个区域，在大小允许时一次请求处理，并明确各自 ID。多对象不应该默认意味着多倍启动、多倍遍历、多倍模型往返。

UIA 本身也有明显可优化空间：你现在每个原生动作还可能重新遍历整棵树。应逐步收敛到一个常驻原生宿主，感知和操作共用对象定位机制；先查指针附近或目标子树，批量获取需要的属性，变化后局部刷新。微软已经提供 BuildCache 一类批量读取能力，没必要靠反复逐节点跨进程调用。卡死的探针要能隔离重启，不能只停止等待、让后台线程继续堆积。

自绘界面不能靠「把 UIA 再试几遍」解决，也不能把整个应用粗暴归成「只能视觉」。我建议按区域判断能力：菜单可能有结构，画布没有；文字可以 OCR，图标和布局需要视觉；真正的业务对象可能来自插件。已经确认无结构的区域，下次直接走相应路线，不再先等几秒超时。视觉在这里不是所有方法失败后的急救，而是一条正常执行路线。先用现成能力验证，暂时不要为「通吃所有自绘软件」训练自己的大模型。

坐标问题则必须从规则上消灭，不能再靠加偏移量修补。你需要一套统一的坐标转换契约：每个点和矩形都带所属空间、窗口或显示器、帧 ID、转换版本，禁止裸四元组在模块间随意流动。系统缩放、窗口局部坐标、浏览器页面缩放、截图裁剪、图片缩放和补边，都由这条转换链负责，模型不做 DPI 算术。特别是混合缩放双屏，不能用一个全局 scaleFactor 乘所有坐标；Electron 的转换本来就是按所在显示器进行的。

具体落地，Windows 原生进程和线程要核对 Per-Monitor V2 DPI 环境；模型在缩小截图上给出的点，必须通过实际裁剪、缩放和补边记录反算，再交给系统输入。Mac 单独处理 points 与截图像素的转换，不要照搬 Windows 的「全局物理像素」假设。给这层做往返测试，再在双屏、负坐标、125%／150%／200%、跨屏拖动窗口中实际点击校验。统一的是转换协议，不是强迫所有平台使用同一种原生单位。

还有一个需要特别检查的时间问题：冻结截图，只能证明图片属于那个时刻，不能证明几秒后读到的 UIA 文本也属于那个时刻。按你的说明，现在窗口身份校验很充分，但同一个窗口里的内容仍可能已经变化。建议明确分开「用户当时指的材料」和「现在可以操作的界面」：前者保留历史证据，后者每次行动前重新确认。异步读取要保留自己的时间和版本，不能因为 HWND 相同，就贴到旧截图上当作同一时刻。

执行时，不要只选「每步截图重想」或「连续盲点」两个极端。已确定的一小段操作本地执行，遇到弹窗、目标移动、焦点变化或用户接管就停；用本地事件和目标区域的轻量变化检测决定是否重新观察。等待的是「这个目标可操作」，不是「整个屏幕完全静止」。Playwright 的可见、稳定、可接收事件等检查就是可借鉴的工程做法，不必先训练一个等待模型。

办公场景尤其应该绕开不必要的点击。读写 Excel 用单元格和区域，修改 Word 用文本范围，调整 PPT 用幻灯片对象；界面负责确认位置和呈现效果。跨平台可以优先评估 Office.js，Windows 已有的 COM 路线则保留在平台适配层，具体能力按版本检测。但必须分清「磁盘文件」和「用户正在编辑的未保存文档」，不能读旧文件、改旧文件，最后覆盖用户的新内容。Office 官方提供的就是对文档对象直接读写的接口，而不是要求逐个点击控件。

长任务的「智能」，我会先落实成一份真正参与执行的任务清单：目标是什么、哪些东西不能改、哪些步骤已验证、哪些只是尝试过、卡在哪里。完成一步就写入结果证据；用户中途说「不要覆盖原文件」，后续动作立即受这个约束。失败后呈现「已写入 12 行，剩余 3 行未处理，原文件未覆盖」，而不是一堆工具日志。你的 PDF 里关于约束丢失和接管成本的分析，最应该在这里变成产品能力。

可信任不等于每一步都弹确认，也不等于读不到就终止。建议按后果处理：读取和生成预览尽量顺畅；可恢复修改提供差异和恢复点；发送、覆盖、删除等关键动作确认具体对象与后果。超时之后先查真实结果，再决定重试，避免重复提交。屏幕上的文字始终是待处理内容，不能因为写着「执行某条命令」就获得权限；这一点必须由执行层限制，不能只靠给模型加一句提醒。

Win/Mac 可以共享任务状态、对象引用、模型调用和权限规则，但截图、无障碍、输入控制分别实现。Windows 先把现有原生宿主做好，Mac 再接 ScreenCaptureKit 和系统无障碍接口，不要为了跨平台立即重写整个项目。另外，Windows 上涉及真实键鼠的任务，不应承诺「你继续随便操作，它在后台干活」；连 OpenAI 当前的 Windows CU 文档都明确是前台接管。MP 更合理的体验是短暂接管、随时暂停，结构化后台任务则尽量不抢鼠标。

产品上线顺序，我建议先把「单对象读取并解释」「多对象比较并输出」「结果预览后写回」做成三个可靠闭环。比如跨窗口比较几份报价并生成 Excel，指着一段内容改写后回填，把通知里的信息整理成可检查的待办。这些短任务可以组合成复杂办公流程，也容易让用户第一次使用就理解价值。入口先保证点选、原生选区、框选稳定，手绘圈线作为增强，不要让用户必须画一个符合算法阈值的圈才能使用 AI。

验收也要换口径：不是「几十个单元测试通过」，而是你现在失败的真实任务，在打包后的软件里能否重复完成。把输入法弹窗、多笔删除、窗口移动、断网、取消、模型不可用、混合 DPI 都加入回放。每次失败自动生成经过脱敏的诊断包，明确停在哪一层。可以先设工程目标：100 毫秒内有交互反馈，正常结构化命中的大多数请求在一秒左右交付对象；这是待验证的目标，模型耗时另外统计，不能靠动画掩盖。

最后，「比 Astra 更省、更准、速度接近」必须落到同一批真实任务上算账：统计完全完成率、总耗时、用户接管时间和每次成功交付的总成本，而不是只比较单次模型价格。先用同一个强模型对比 MP 和最简 CU 实现，确认你的封装没有拖后腿，再逐步换便宜模型、加入缓存和可复用流程。推广时先找一小批每天真做这些工作的用户，用未经剪辑的成功任务展示价值。真正值得积累的是用户授权保存的业务规则、对象映射、模板和经过验证的流程；一个炫酷光标容易被替代，一套能在用户现有软件里稳定交付工作的习惯，才更有留下来的理由。

## 我对 A1 的核对结果

**A1 里被代码证实为真的**：快照桥仍吃 64 KiB 默认上限；`element:` 锚点在当前路径上必然失败；多笔各自跑完整结构化读取再各自 OCR 再逐笔 Look；每个原生动作都要重新遍历整棵树；没有选区绑定时「非空文本 = 命中」；「界面允许提交，最后才发现模型不能读图」确实发生过。这些我不只是认同，我逐条找到了位置（下面）。

**A1 里我要改的**，按重要性排：

### 【修正 1】64 KiB 不是「上传限制」，而且把上限抬高本身不是正解

先纠正一个用词，因为它会带偏后面的所有判断。`scripts/_bridge_common.py:16-19` 里的两个数字是 **Electron 与 Python worker 之间的本地 JSON 传输预算**，跟「上传」「模型上下文」都没有关系：

```python
MAX_BRIDGE_PAYLOAD_BYTES = 64 * 1024          # 65536，其它桥用
MAX_SELECTION_PAYLOAD_BYTES = 8 * 1024 * 1024 # 8388608，本次为 selection 桥加的
```

`scripts/selection_bridge.py:159` 已经改用 8 MiB；`scripts/selection_snapshot_bridge.py` 的 `read_payload()` **仍然是裸调用**，吃 64 KiB 默认值。超限时返回 `{"ok": false, "error": "payload_too_large"}`（`selection_bridge.py:3382`），Electron 侧翻成 `electron/stage_contract.ts:227`：

```
payload_too_large: '这次选中的内容太大了。请缩小范围再试。'
```

用户看到的这句话与「选区太大」无关，它说的是 JSON 字节数。所以 A1 说的「管道问题」是对的。

**但比这更重要的一点 A1 没说到**：payload 之所以能撑到 64 KiB 以上，是因为**同一份证据被复制了 N 份**。`scripts/selection_snapshot_bridge.py` 的 `_capture_stroke_materials` 为**每一笔**存一份 `context.to_dict()` 加**整条 `perception_trace`**；而 `AdapterReadContext.to_dict()` 会带 `content` 与 `artifacts`（里面可能有 `selection_context`、最多 64 个 `region_elements`、最多 24 个 `captured_rects`）。三笔就是三份，而这三份描述的是**同一个窗口、同一张冻结帧**。

所以正解不是「把 64 KiB 调到 8 MiB」，而是：

1. 共享的东西只存一份（窗口清单、帧路径、帧 bbox、公共 trace），每笔只带自己的 `index` 与 `bbox`；
2. 大材料一律走**引用**（路径 / snapshot id / reference id），不把内容塞进 JSON —— 你原话说「主要就是提供一个文件路径啊，这是感知层，不是实现」，代码其实已经是这个方向（`app/grounding/explorer_context.py` 的文件头就写着「内容摄取稍后发生，在用户的指令说明要做什么之后」），破坏这条原则的是多笔复制；
3. 上限**统一**，并且错误必须带请求 id（`scripts/selection_worker.py` 里有一层更粗的 `_MAX_LINE_CHARS` 超限错误，它的 `id` 是 `None`，而 `electron/selection_worker_client.ts` 按 `message?.id !== active.id` 过滤 —— **这条错误匹配不到任何请求，最终表现为沉默超时**。这正是 A1 说的「不能被过滤后变成沉默超时」，只是它有具体位置）。

顺带说一句你的直觉是对的：**这层不该有「上限」这个概念存在感**。感知层产出的是「对象 + 引用 + 少量文本」，几十 KB 就足够了；一旦超过，说明哪里复制多了。

### 【修正 2】覆盖判据那条 A1 说对了，但结论要分层，不能一刀切成「不算命中」

位置在 `app/grounding/marked_read.py:137`：

```python
mark = _rect(mark_bbox)
rects = [r for r in (...) if r]
if mark is None or not rects:
    return MarkCoverage(True, "structured_text")   # ← 没有几何 = 算命中
```

没有几何时，非空文本直接判命中；而 `app/perception/fusion.py` 的 `pixel_tier_warranted` 第一条就是「有 `marked_content` 且非容器 → **不派像素层**」。所以「读到整篇文章」确实会压掉视觉补读。A1 说得对。

但这个分支是**刻意留的例外**：Word COM、DOM 读取这类来源有真文本、没有几何，一刀切成 `False` 会把它们全废掉（`marked_read.py` 的 docstring 专门解释了这点，并写明「几何只用来减分，从不用来加分」）。

所以我采纳 A1 的方向、改掉它的力度，落成三层：

- **有显式绑定**（原生选区 / 单元格地址 / DOM 选择器 / 文本范围 / 文件路径）→ 允许不依赖几何，直接算命中；
- **只有自由文本**（UIA 返回一段字符串，没有 rects）→ **降级为「上下文」，不算命中**，像素层照跑；
- **两个概念分开成两个字段**：`读到了这个窗口的内容` 与 `已绑定到用户指定对象`。A1 这句话说得好，直接采纳，而且 `fusion.py` 的 trace 已经有 `readState` / `marksCovered` 两个位置可以承载。

### 【修正 5】「规划模型与视觉模型独立配置」与现有决定冲突，要显式改而不是默认改

代码现在是明确的单模型约定：`app/ai_client` 那侧对纯文本模型返回「当前模型 … 是纯文本模型，无法读图。请在模型菜单选择支持图像输入的模型。**文字和图像使用同一个所选模型。**」A1 建议「规划模型和视觉读取可以独立配置」。

### 【修正 6】「中间随时点一下」和「多笔连续」撞的是同一个瓶颈，而且比 A1 说的更好修

## A2

你这次指出了真正的边界：MP 不是「先把所有东西识别完，再启动一次 Agent」，而是让正常 Agent 在做事的全过程中，随时接得上人的指点、补充和当前现场。上一轮我把感知和执行混在一起了。把 64 KiB 改成 8 MiB 只是补管道，不是正确的产品方案。

我查到了 farzaa/clicky，也检索了作者的 X 发布信息；X 原视频没能直接播放，因此内部实现判断依据公开源码。先提醒一个重要变化：作者在 2026 年 4 月 27 日明确表示，已有代码继续按 MIT 开放，后续新功能转为私有；现在官网已经同时提供「指导你操作」和「Agent 替你做事」，不能再把它当成一个只会教学的项目。

Clicky 公开版的核心其实很直接：按键说话，流式转录，截取屏幕，连同最近对话交给 Claude；回复附上目标坐标，蓝色箭头飞过去，再播放语音。它这条主链每轮都看截图，并没有先等待多层 OCR、结构解析全部完成。截图会缩放，坐标由程序映射回对应显示器。值得借鉴的是短链路，而不是把它想成有某种神秘的系统级智能。

但「指给人看」和「替人操作」的可靠性要求不同。箭头偏一点，人通常会自行理解；自动点击偏一点，可能就改错文件。所以 MP 的双生鼠标应该共用一套对象定位，但分开表达和执行：同一个目标，既能用于「指着这里讲解」，也能用于「实际执行这一步」。不要让教学箭头和自动操作各找一次目标，否则你看到它指对了，真正点击却可能是另一处。

双生鼠标也不必实现成两个争抢系统输入的真鼠标。Clicky 的公开实现就是一个不抢焦点、鼠标事件穿透的透明覆盖窗口，Electron 也有相应能力。建议你的鼠标始终代表人的意图，另一只代表 Agent 当前关注或准备操作的位置；只有实际操作时才取得输入控制权，人接管就暂停尚未执行的动作。两个箭头可以同时存在，但这不等于可以在任意软件里安全地同时操作。

关于文件，你说得对：本机 Agent 应拿到真实路径，然后按需读取，而不是把文件内容塞进感知层的 JSON。你的文档也明确写了，8 MiB 是本地传输预算，不是文件或模型上下文预算。正确做法是小消息传引用，大材料留在本地；远端 Agent 才通过桥接工具按需取内容。内部仍需防止异常消息撑爆进程，但自动分块、引用传输应该由软件承担，不能让用户反复缩小圈选。

微信里的 HTML 文件，应该按「找到原文件」来处理，而不是把文件卡片描述得更详细。我的建议是先尝试取得客户端暴露的文件引用；没有直接引用，就用可见文件名、大小和相关时间，在实际配置的下载目录中查候选。重名时不能随便拿第一个；客户端提供「打开所在文件夹」等入口时，可以让正常 Agent 完成这个小动作，再接资源管理器取得路径。这里不用把微信内部目录写死，更不用一上来读取聊天数据库。最终应交付「原文件已定位并可读」，或「已经锁定这张文件卡片，尚需取得文件」，后者也应允许 Agent 继续解决，而不是感知失败就整轮结束。

还有一个与你这次纠正直接相关的现状：按代码说明，你的手势入口会把 workspace_root 设为空、advanced_tools 设为 False，项目和 Shell 工具另需进入 Studio。这意味着「材料交给正常 Agent」目前并没有自然成立。建议手势入口沿用当前任务已经授权的正常运行环境；需要新增权限时只处理那次权限差异，不要因为用户从鼠标入口进来，就切换成一套能力缩水的 Agent。

「Google 能连续说 and this，是因为它拥有操作系统，Win/Mac 做不到」，这个判断要改。系统整合可以减少接入摩擦，但连续指代本身主要是会话和状态管理问题。Google 公开强调的也是指点、语音和共享上下文；Claude Agent SDK 已经提供持久会话、排队输入和中断机制。你不需要先拥有一个 AI 操作系统，才能做到这一点。

你的现有说明里已经能看到两个具体断点：提交命令通常创建新 taskId，而 taskId 一变，指代 episode 就重建；同时，worker 有正在运行的请求时，新请求会直接返回 busy。所以现在不只是「记忆不够强」，而是每说一句话可能被当成新任务，而且执行期间入口还被堵住。这不能靠扩大上下文、加向量库或超图修好。

应该改成「一个持续任务，接收很多次输入」。你说「把这行加入采购表」，任务保存目的表、添加方式和已完成结果；下一次划线说「还有这个」，只增加一个新对象，沿用前面的操作。第一项还没完成，第二项可以排队；你说「不是这个，是那个」，就是修改当前对象，而不是新开任务。每项都有独立身份和执行回执，避免重试时重复加入。任务结束、麦克风关闭、鼠标提示隐藏，也不要再当成同一件事。

中途指点必须是一条独立通道，不能排在长任务后面。你一点、一说「这里不对」，本地先接收并显示「已收到纠正」，暂停相关的后续操作，再把新对象和新要求交给 Agent。后端不能在当前推理中追加输入时，就取消该次推理或在下一个安全边界重新规划；已经执行出去的操作要核对结果，不能假装撤销成功。现有的 add、correct、remove 和 next-step 数据结构已经有了，优先把它们真正接入运行中的任务，而不是再设计一套平行协议。

交互上，我建议一次唤醒后保持会话，不要求每句话重新晃动鼠标。会话内，语音「这里」附近发生的点选自动与这句话绑定；普通操作则照常留给原软件。纯粹指代、又不希望真的点击底下控件时，用一个轻量的指代手势，例如鼠标侧键配合点选。这个区别必须存在，否则你想指着「删除」问问题，却真的触发删除。目标不是增加模式，而是让用户随时插话，同时不破坏原来的工作习惯。

你说的三秒实况值得优先做，而且三秒应该是默认时长，不是新的硬限制。建议在用户开启的协作会话里，对授权窗口保留最近几秒的本地循环缓存；触发时固化「之前两秒加之后一秒」，也支持按住录制并延长。这样「刚才闪了一下」的问题也能留下来，不必要求用户先猜到问题再开始录屏。Windows.Graphics.Capture 和 macOS ScreenCaptureKit 都提供连续屏幕采集能力，这部分不需要等待新的模型突破。

这里最容易做错的是：传了视频，以为模型就看到了全过程。Gemini 官方文档明确写了，默认静态视频处理按每秒一帧采样，快速变化可能丢失。你的方案应保留原始短片，在发送时根据任务选择带时间戳的连续帧，尤其保留变化发生前、中、后的画面；支持视频的模型可设置采样策略，不支持的就发送有序多图，并允许补取具体时刻。闪烁和动画问题不能一律被压成两张首尾截图。

这项能力与 CU 应该共用底层，而不是做成另一个录屏工具。人触发时，它是「把问题过程交给 Agent」；Agent 执行时，它帮助判断「刚才操作后发生了什么」。但动态画面只是现象证据，修 bug 还需要相关日志、文件或源码。MP 的优势应该是把这些证据关联起来，让后续 Agent 少猜，而不是只生成一段「画面发生了闪烁」的漂亮描述。

主动性方面，我建议你把「发现值得做的事」和「决定现在动手」分开。比如采购表已经更新，但引用它的 PPT 仍是旧数字；或者上一个任务缺的附件终于下载完成。前者产生一个需要更新的候选任务，后者恢复已有任务。已经授权的范围内自行完成，范围外才询问。不要靠每隔几秒把全屏发给模型问「有什么可以帮忙」，那既贵，也很容易烦人。

动态超图可以用在这里，但不是因为「图越复杂越智能」。它真正有用的地方，是把一次工作的客户、附件版本、目标表格、PPT 页面、约束和执行结果放在同一组关系里。附件变了，就知道哪些输出可能过时、哪些步骤需要重做；你说「还是昨天那个客户」，能找回对应任务，而不是只搜到一段相似聊天。这也是我建议 MP 重点积累的持久记忆：对象身份、版本依赖、用户纠正和成功做法，不只是聊天摘要。

实现上可以先用本地事件记录和关系表表示这些多方关系，不急着部署大型图数据库。事实保留来源和有效时间，用户明确要求与系统猜测分开，旧版本被替代而不是悄悄覆盖；这些时间与来源管理思路可以参考 Graphiti。至于「何时主动提醒、何时准备草稿、何时直接执行」，仍需单独的判断策略。先让它在后台记录本来想提出的建议，验证是否真的有用，再逐步开放主动动作；评价的是省下多少工作、造成多少打扰，不是每天提出多少条建议。

竞争上，不能再把「有记忆、会学习技能、会定时执行」当作独有卖点，Hermes 已经公开把这些列为核心能力，Claude 的 SDK 也支持持续交互。我的建议不是逼用户离开它们，而是让 MP 能给它们提供桌面对象、实况证据、双向指点和可靠操作，同时保留自己的完整产品入口。MCP 可以提供工具，但中途纠正和会话续接还需要 SDK、运行控制器或对应宿主的接口；仅仅装一个 MCP，并不会自动变成实时协作。

获客上，我会先押「屏幕问题直接交给现有 Agent」这个入口，尤其是开发、设计和办公软件里的具体问题。演示不要只是箭头飞来飞去，而是一条完整故事：界面闪烁，你点一下说「这里有问题」；MP 带上几秒过程和相关材料，Agent 开始处理；中间你说「不是布局，是这个动画」，它立即改方向；处理完展示修改和验证结果。这个故事既能吸引已经使用 Claude Code 的人，也能自然延伸到复杂办公，而不是把产品锁死在教学助手上。

下一版的验收就围绕这条主线：微信指到文件后能取得可读原件；连续添加多次材料不丢目标、不重复执行；长任务中途能纠正而不必重启；短暂异常能被实况保留下来；用户接管后 Agent 能基于新状态继续。再用同一个模型比较原生 Agent 与接上 MP 后的完成率、总耗时、前台占用和用户介入时间。不能靠增加人的操作，把成本藏起来。

所以我对 MP 的定位建议是：可随时指点和接管的自动化助手，而不是必须有人一直陪着的助手。人不干预时继续做，人随手一点就能改变方向，下次还能沿用上次确认过的做法。双生鼠标负责让人看懂它，持续任务负责让它不忘事，实况证据负责让它少猜，主动性负责让它在真正需要时开始做事。这四者接成一条可靠链路，比单独再加一个「更强感知模块」更接近你的破局点。

## 我对 A2 的核对结果

**先补一个 A2 没说透、但对「为什么 clicky 快」最关键的事实。**

我核对了 clicky 的公开仓库：它是 **macOS 专用的 Swift 菜单栏应用**（`NSPanel` 全屏透明覆盖窗），按键说话 → AssemblyAI 流式转录 → 把**转录 + 一张截图**发给 Claude（SSE 流式）→ 回复里带 `[POINT:x,y:label:screenN]` 标签 → 光标飞过去 → ElevenLabs 念出来；三个 API key 走 Cloudflare Worker 代理；MIT，2026 年 4 月 27 日之后新功能转私有。

**它快的原因不是「视觉用得少」，而是它根本没有感知栈。** 每一轮就是「一张截图 + 一句话」直接进 Claude，没有 UIA、没有 OCR、没有 fusion、没有 grounding、没有证据契约。而我们这边，一次圈选要经过：结构化 tier（最多 2 秒）→ 像素 tier（最多 12 秒）→ 融合仲裁 → grounding → 再融合一遍 → 逐笔 Look。**这不是「Astra 很聪明」，这是「我们没有把默认路径留短」。**

所以你问「他能做我们能不能做」——能，而且我们**已经有**他所有的零件（透明覆盖窗 = `agent_cursor_window.ts`，箭头 = agent cursor channel，坐标标签机制 = `geometry_space.ts`）。我们要补的不是能力，是**把「一张图 + 一句话」这条最短路径变成合法的一等公民**，结构读只作为加速器（命中就省一次模型调用），而不是必经的关卡。

**A2 里被代码证实的**：taskId 一变 episode 重建；worker 忙时新请求返回 busy；手势入口 `workspace_root=""`、`advanced_tools=False`；add/correct/remove/next-step 数据结构已存在；`Steered`/`FollowupContinued` 说明中途接入的机制已存在。这几条我都逐条查了，准确。

**A2 里我要改的**：

### 【修正 12】「8 MiB 不是正确方案」这句对，但理由要换

A2 说「改 8 MiB 只是补管道，不是正确的产品方案」——结论对，但它把 8 MiB 说成「扩上限」。真正的重点在【修正 1】：**感知层本来就不应该传内容，只传引用**；现在之所以超限，是因为多笔把同一份证据复制了 N 份。修的是复制，不是数字。你的原话「主要就是提供一个文件路径啊」就是这条原则的正确表述，可以直接写成团队规则：**感知层的输出里不允许出现超过 N KB 的自由文本，只能出现路径、ID、坐标与短标签。**

### 【修正 13】微信 HTML 文件：A2 的方向对，但有一半 capability 已经在手边

A2 建议「先取客户端暴露的文件引用 → 用文件名/大小/时间在下载目录查候选 → 重名不要随便拿第一个」。方向完全同意，且第三点是关键（拿错文件比读不到更糟）。

补充两点代码事实：
1. 「文件名 → 真实路径」这件事，桌面路径上已经做过：`app/grounding/explorer_adapter.py` 的 `resolve_child_path` 已经处理了大小写、尾部省略号、Unicode 标点被 UIA 破坏（把 U+FFFD 替换成空格）、互为子串等等，而且桌面目录是用 `SHGetFolderPathW` 取的**真实**桌面（注释里就写着「`Path.home()/Desktop` 在桌面被重定向的机器上是错的，比如这台机器真实桌面是 `D:\Desktop`」）。微信下载目录那一路可以直接复用同一套匹配规则。
2. 第二条出口 A2 说得很对：「**已经锁定这张文件卡片，尚需取得文件**」也必须是一个合法状态，让 Agent 继续，而不是感知层判失败就整轮结束。现在 `app/input_artifact/schema.py` 的 facts 里已经有 `local_file` 这一类事实，把它拆成「路径已确认」与「仅有候选」两种 kind 即可承载。

### 【修正 14】「不要因为从鼠标入口进来就切换成能力缩水的 Agent」——同意原则，但这是权限决定，不是 bug

`scripts/selection_bridge.py` 里那两行是**有人写下的安全决定**，注释原文是「A screen gesture authorizes the pointed material, not the persisted coding workspace. Project/shell tools require an explicit advanced project choice in Studio.」所以正确的改法不是把这行删掉，而是：**沿用当前任务已经获得的授权**（任务上下文里的授权范围），只在需要**新增**权限时处理差异。原则同意 A2，落法不同——不能变成「鼠标入口 = 全权限」。

### 【修正 15】多笔连续：比 A2 说的更接近能做成

A2 说「这不能靠扩大上下文、加向量库或超图修好」——完全同意，而且**数据模型已经是为这件事设计的**：`app/context_pack/sources.py` 有 `TIMELINE_KINDS = {utterance, point}`（把「说了什么」和「指了哪里」放在同一条时间线上），`TASK_INPUT_TARGETS = {next-step, next-turn}`，`ReferenceUpdate.operation ∈ {add, correct, remove}`。`electron/interaction_episode.ts` 的 `bindCommandTarget` 已经在多区域时逐笔建 source（`source:{base}:{index}`）与 reference。

缺的是三件事，且都是局部的：
1. **任务保持**：`bindCommandTarget` 现在 `taskId` 一变就 `start(now)`；改成「指令未显式开启新任务时沿用」；
2. **输入队列**：worker 单飞（`selection_worker_client.ts`）改成可排队 + 可打断；
3. **每项的独立回执**：避免重试时重复加入（A2 这条说得好，采纳）。

### 【修正 16】「双生鼠标共用一套对象定位」——这条我完全同意，而且是本轮的抓手

A2 说「不要让教学箭头和自动操作各找一次目标，否则你看到它指对了，真正点击却可能是另一处」。这句话在我们代码里有一个**现成的反例**必须修：`app/agent_runtime/look_tool.py` 里 `bbox:` 是模型自己编的坐标，`reference:` 才走真实解析；`app/perception/element_handles.py` 的句柄是给人看的，没有接回 look。**同一个对象在「指给你看」「读给你听」「点给你用」三条路上是三个不同的定位过程**。统一成「一个对象 ID → 一个定位结果」，三条路共用，这就是双生鼠标真正的技术含义。

### 【修正 17】「MCP 装上去不等于实时协作」——同意，补一句为什么

MCP 是**请求-响应**的工具面：Agent 调一次、拿一次结果。而「你随手一点，正在跑的任务改方向」需要的是**主动推事件进正在运行的会话**。我们这条链上对应的东西是 `Steered` 事件 + worker 的输入通道，不是 MCP。所以对外暴露能力可以用 MCP，但**实时协作必须走宿主/运行控制器**——A2 这个判断是对的。

### 【修正 18】验收主线的五条，我建议再压一遍

A2 给的下一版验收（微信文件取得原件 / 连续添加不丢目标不重复执行 / 中途纠正不必重启 / 短暂异常能保留 / 接管后能续）方向对。我会改成五条**可当场判定**的：

1. 指着微信里一个已下载的附件，能给出**可读的真实路径**（或明确说「只找到候选，需要确认」）；
2. 连续三次「划线 + 一句话」，三次都进**同一个任务**，材料数为 3，没有重复执行；
3. 任务跑到一半，用户点一下说「不是这个」，**不重启、不重读全部材料**，只有那一步改方向；
4. 一个 2 秒的界面闪烁，能被一键固化并交给模型，且**不要求用户提前开录屏**；
5. 用户接管鼠标后，Agent 基于新状态继续，**不假装撤销已经发出去的动作**。

这五条正好覆盖你说的「简单任务都报错」的全部实际形态。

# 我的结论（TLDR）

1. **clicky 快，不是因为它更智能，是因为它没有感知栈。** 一轮 = 一张截图 + 一句话 + 一个坐标标签。我们的默认路径要缩到同样短：**截图直连模型是默认，结构读只在能省一次模型调用时才用**。所有零件我们都有（透明覆盖窗、箭头通道、坐标换算），缺的是把这条路定为一等公民。

2. **「感知层不该有上限」这句话要落成规则，而不是调数字。** 感知层输出只允许路径 / ID / 坐标 / 短标签；现在超限的根因是**多笔把同一份证据复制了 N 份**（每笔一份 context + 整条 trace）。修复制，不是修 64 KiB。

3. **「简单任务随机失败」的三个真实来源都在工程层，不在模型层**：快照桥仍吃 64 KiB 且错误文案误导（`stage_contract.ts:227`）；worker 单飞导致第二次输入被打回、且超限错误 `id=None` 被过滤成沉默超时；`withKeptStrokes` 删笔画不同步材料。这三条与换什么模型无关。

4. **「非空 ≠ 读到了」还差最后一层**：`marked_read.py:137` 在没有几何时直接算命中。要按「显式绑定 / 自由文本」分层，并把「读到了这个窗口」与「绑定到了用户指的对象」拆成两个字段。

5. **你设想的「随时点一下 + 连续 and this」不需要新协议**：loop 层已有 `Steered`，数据层已有 `timeline(point/utterance)`、`next-step`、`add/correct/remove`。缺的是**任务保持 + 输入队列**两件局部改动。

6. **坐标要一次收干净**：四套表达（LTRB / XYWH / 物理 / DIP）必须显式标注来源与空间；`system_context.py:22` 现在还是 Per-Monitor **v1**，混合缩放屏会拿错 DPI；抄 clicky 的做法——**让模型永远在「它看到的那张图」的坐标系里说话**，换算全由代码做。

7. **实况帧别做成录屏**：表示成「带时间戳的帧数组」，走 `Look` 已有的多图机制（`FileVisionBackend` 的 `labeled_extra_images` 现成），模型侧不需要支持视频。

8. **主动性先只加一条边**：`产出 ← 依赖 ← 某个 source 的 revision`。有了它，「附件更新 → 哪些产出过期」才成立；没有它，动态超图只是好看的聊天摘要。

9. **验收换口径**，并且现在就有一条实例：`tests/selection_bridge_test.py` 里那个红用例，正是「新行为已生效、旧契约没人清理」——这种冲突就是随机失败的温床。

10. **A1/A2 的大方向我认同**：先做牢最短闭环、对象身份、失败语义、坐标契约，再谈复杂任务与主动性。我不认同的是**优先级和落法**：不要把「独立配置视觉模型」「Office.js」「大型图存储」排在前面；先修那些「跟换什么模型完全无关」的错误。
