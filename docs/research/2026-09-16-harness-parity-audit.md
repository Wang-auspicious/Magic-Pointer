> 结论先行：MP 的 loop 在**治理**（权限、效果、回执、会话账本）上比三家都细，但在
> **活下来**的机制上缺了三件最基本的东西——(a) 上下文溢出后能救回来的路，
> (b) 输出被截断后加大上限而不是丢掉这一轮，(c) 压缩失败时不要静默把历史换成一句报错。
> 复杂任务死在 (a)(b)(c)，不是死在工具不够多。

## Why Magic Pointer stalls on complex tasks

按「能多快把一个复杂任务打死」排序。每条都给了可复现的代码路径。

### RC-1（致命）压缩失败时，整段历史被一句报错字符串替换

`_summarize_history` 调 `ask_text_model(...)`（`scripts/selection_bridge.py:2775-2784`、`scripts/conversation_bridge.py:924-938`），外面套 `try/except → return ""`。
**但 `ask_text_model` 从不抛异常，它把失败当成字符串返回**：
`app/ai_client.py:732` `return f"AI 调用失败：HTTP {code}。\n{detail}"`；
`app/ai_client.py:735` `return f"AI 调用失败：模型回答超过 {seconds} 秒，本次已停止等待；端点没有因此被判为离线。"`。
于是 `except` 是死代码，那句中文报错成了**非空摘要**，在 `app/agent_runtime/memory.py:221-253` 被包裹成 `[前文摘要]\nAI 调用失败：…` 并替换掉 `[condensed, *tail]` 的全部 head。

放大这个 bug 的三个参数：总结器 `timeout_s=25.0`、`attempts=1`、`max_tokens=1200`（`selection_bridge.py:2780-2781`；`ai_client.py:592`）。一个 48_000 字符（`app/agent_runtime/compaction_prompt.py:24`）的中文历史交给 25 秒一次、限 1200 token 的调用——超时是常态而非例外。

**后果链**：压缩「成功」（列表长度确实变短，`loop.py:973-975` 按 token 判定通过）→ `fruitless_compactions` 归零（`loop.py:994-1000`）→ 模型收到一份内容为报错文本的「前文摘要」→ 它不知道自己在干什么，于是重复劳动或乱调工具 → 触发 `tool_guardrails` 的重复证据判定 → `STALLED`（`loop.py:1750-1759`）。用户看到的是「跑到一半突然失忆然后停住」。

### RC-2（致命）没有上下文溢出的救援路径，而且压缩会自我永久禁用

两件事叠在一起：

(a) **溢出只能死**。全仓库 grep `prompt_too_long` / `context_length_exceeded` / `maximum context` 零命中。provider 因超窗返回 4xx 时，`StreamingMessagesBackend._post_streaming` 只做一次「去掉可选字段重试」（`model_client.py:1134-1146`），然后 yield `TurnWithheld(reason="backend_error:http_400")`。`loop.py:1097-1119` 只把 `backend_error:http_5*` 当可恢复，400 直接落到 `loop.py:1169-1177` 的 `PROVIDER_UNAVAILABLE`。
对照：CC 有三级自愈（`src/query.ts:1094` collapse drain → `:1120` reactiveCompact → 都失败才报错且跳过 stop hook）；dsh 在 `agent/request-error` 上认 `CONTEXT_WINDOW_EXCEEDED_CODE` 后**绕过阈值直接压并重试**（`compaction-basic/src/index.ts:179-223`）；Hermes 把 `context_overflow` 归到 `should_compress=True`（`agent/error_classifier.py:51,91`）。

(b) **压缩 2 次无效就永久关闭**。`loop.py:950-966` 的 if 有一个合取项 `fruitless_compactions < _MAX_FRUITLESS_COMPACTIONS`（`_MAX_FRUITLESS_COMPACTIONS = 2`，`loop.py:224`），而 `fruitless_compactions` **只在这个 if 体内才会被归零**（`loop.py:994-1002`）。一旦到 2，这个条件永远为假，计数器再也不可能减——本次 `run_agent_loop` 的剩余全部回合都不再尝试压缩。注释说这是「防止对一个不会缩小的历史每轮重复总结」的 anti-thrash（`loop.py:225-230`），但反 thrash 计数器**没有重置出口**是设计缺陷：模型换了个方向、清掉大批 tool 结果之后，压缩不会回来。

组合后果：一个有真实进展的长任务在第 3 次逼近窗口时进入「不压缩 + 溢出即死」区间。用户描述「复杂任务里跑不起来」正是这一段。

### RC-3（致命）max_tokens 硬编码 4096，且截断的处置是丢掉整轮

`_apply_model_client` 里 `max_tokens=int(config.get("max_tokens") or 4096)`（`app/harness/builtin_bundle.py:614`），两个桥的 row 都写死 `"max_tokens": 4096`（`builtin_bundle.py:1068`、`:1251`），子代理默认也是 4096（`app/agent_runtime/subagent.py:42`）。

对照：CC 默认 8000，**命中后立刻用 64000 重发同一请求**（`src/utils/context.ts:24-25` `CAPPED_DEFAULT_MAX_TOKENS = 8_000` / `ESCALATED_MAX_TOKENS = 64_000`，提升逻辑在 `src/query.ts:1199-1221`，还有 `tengu_max_tokens_escalate` 事件）；dsh 的 provider 默认输出上限是 32768 / 256000（`llm-pi-ai/src/config.ts:41`、`llm-deepseek/src/adapter.ts:89-93`）。

MP 遇到 `finish_reason == "length"` 时走 `_parse_sse:1444-1445` → `TurnWithheld("max_output_tokens")` → loop 丢掉这一轮、注入恢复语、**用同一个 4096 上限重来**（`loop.py:1189-1207`），连续 3 次就终态失败（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`，`app/agent_runtime/errors.py:13`；判在 `loop.py:1178-1188`）。上限从头到尾没变过。

写一个 200 行的文件、一次长 Patch、一段长 Bash 输出总结——4096 输出 token 在中文下大约 4000 字。复杂任务的高频操作全部落在截断区。而 CC 的做法（同请求加大上限重发）在 MP 里**一行都没实现**。

### RC-4（严重）单结果 64k 字符、无回合聚合预算；一轮并行灌进 256k 字符

`_MAX_TOOL_RESULT_CHARS = 64_000`（`loop.py:279`），裁剪在 `_bounded_tool_result`（`loop.py:2641-2678`）。`max_parallel_tool_calls = 4`（`app/fabric/engine.py:1040`）。四个并行读取各返回 64k 字符 = 一轮 256k 字符；CJK 按 MP 自己的估算器是 1 字符 1 token（`app/agent_runtime/token_estimate.py:40-47`），即约 256k token 在**一次工具轮**里进入历史。

参考都有二级防线：CC 的 `MAX_TOOL_RESULTS_PER_MESSAGE_CHARS = 200_000`（`src/constants/toolLimits.ts:49`），注释直接点名要防的场景是「10 × 40K = 400K in one turn's user message」，且 `enforceToolResultBudget` 在 `src/query.ts:379` 每轮调用；Hermes 按窗口比例给单结果 15%、单回合 30%（`tools/budget_config.py:75-76`），`enforce_turn_budget` 在整批结束时跑一次（`agent/tool_executor.py:1754-1758`）；dsh 是 8192 字符剪枝 + 50000 字节落盘（`compaction-tool-result-pruner/src/index.ts:44`、`spill-policy/src/index.ts:110`）。

MP 把聚合防线交给了「下一轮开头的主动压缩」，而那个压缩会因 RC-2(b) 永久关闭。

### RC-5（严重）工具超时是协作式的，挂住的工具把 loop 永久锁死

`loop.py:2441-2493`：`threading.Timer(spec.timeout_ms/1000, expire_tool)`，`expire_tool` 只做 `timeout_fired.set()` + `scope.cancel_all()`。真正让工具停下需要工具体主动调 `scope.raise_if_cancelled()`，而 token 只是作为 `scope=` 关键字传进 `spec.execute`（`tool_registry.py:493`）。Python 里阻塞在 `subprocess.run`（`app/agent_runtime/coding_tools.py:1518-1528`）的线程不会看这个 token。
更糟的是 `timeout_fired.is_set()` 在 `loop.py:2485` 才被读——也就是**必须等 `execute_tool` 返回**。执行在 `schedule_tool_calls` 的线程池里，loop 阻塞在 `for scheduled in schedule`（`loop.py:1596`）。

### RC-6（严重）「流式」在 Stage 路径不存在，且停止键要等一整轮

### RC-8（中等）失败退避量级与分类面都太窄

MP：`max_provider_retries = 2`（`model_client.py:165`），退避 `0.25 * 2**(attempt-1)` = 0.25s / 0.5s（`model_client.py:352`），无抖动；后端恢复另给 15s / 25s 两次（`loop.py:298-299`）。可恢复判定只有一条：`event.reason.startswith("backend_error:http_5")`（`loop.py:1109-1112`），带进度或 http_5xx 才等，其余 4xx（429 限流、计费、内容策略）一律立即 `PROVIDER_UNAVAILABLE`。

### RC-9（中等）每一轮都在做 O(历史) 的深拷贝 + 全量哈希

`loop.py:1047-1053` 每轮调 `params.session.record_model_request(state.messages, ...)`；实现里 `session.py:1079-1105`：

对一个 300 轮、历史里躺着若干 64k 工具结果的会话，这是每轮数十 MB 的拷贝与哈希。不是致命，但在「复杂任务」的体感上直接变成每轮几百毫秒到几秒的开销。

### RC-10（中等）`…` 截断启发式会误杀整轮工具调用

`model_client.py:62` `_DEFAULT_TRUNCATION_SUFFIX = "…"`；`parse_tool_calls` 在 `model_client.py:410-416`：

`loop.py:1353-1379` 对 `client.last_truncated` 的处置是**把这一轮的全部 tool call 换成"输出被截断，重新生成"**（`_TRUNCATION_MESSAGE`，`loop.py:291`）。
中文模型在一句话末尾用省略号是极常见的（「让我先看一下项目结构…」然后发工具调用）。这个组合会让本来完全合法的整批调用被丢弃、白烧一轮。这个启发式来自 Pi 的 StreamFn 防护，但 Pi 的上下文里它防的是真的流中断；MP 用**文本末字符**当作流完整性的证据，误判率与语言强相关，且没有任何「连续误判」的熔断——`max_output_tokens_recovery_count` 在这条路上被重置为 0（`loop.py:1374`），只有 1000 轮的 `emergency_turn_fuse` 兜底（`loop.py:1355`）。
