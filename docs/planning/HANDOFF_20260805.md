## 1. 这轮最重要的一个发现：UIA 读不到的那批应用，像素也抓不到

用户连续几天报同一个症状：**"只知道是哪个窗口，读不到划的那一行"**（微信、PowerShell 都能复现）。
前几轮一直在读我们自己探针的源码来推断"UIA 能读到什么"——这是错的方法，因为探针有控件类型
白名单、节点预算和多条互斥路径，**"探针没找到"和"应用根本没暴露"从外面看完全一样**。

所以这轮先写了一个**不套任何白名单的只读 UIA 树 dump 工具**，对真实窗口逐个测：

| 应用 | UIA 树 | 能读到划线那行 | 正确路径 |
|---|---|---|---|
| 记事本 | 完整 | 能 | Document 元素 |
| **Edge / 网页卡片** | **完整 DOM 映射成 UIA**，Text/Group/Hyperlink 都带真实矩形，`cls=` 里就是 CSS 类名 | **能** | 现有树遍历即可 |
| **Windows Terminal** | 整个缓冲区只有 **1 个** `TermControl`，`Name` 是 exe 路径 | **能，但必须走 TextPattern** | `RangeFromPoint` → `ExpandToEnclosingUnit(Line)` |
| **微信 4.x（`Weixin.exe`，Qt）** | **整棵树 8 个节点**，消息区是一整块无子节点的 `MMUIRenderSubWindowHW` | **不能** | 只能像素 |

微信实测原始输出（窗口恢复到前台后重测，结果一致，排除"树没建起来"）：

```
root : Window  [615,60 1516x1907]  cls=Qt51514QWindowIcon    "微信"
  Pane         [628,60 1490x1894]  cls=MMUIRenderSubWindowHW "MMUIRenderSubWindowHW"
  TitleBar + 4 个窗口按钮
visited=8  types: Button=4 Pane=2 TitleBar=1 Window=1
```

佐证：wxauto 开源版 README 标注支持 **微信 3.9.X**，不是本机跑的 4.x。

**关键结论（后面所有设计都建立在它上面）**：微信不是特例。Qt、Flutter、GPU 合成的 Electron、
游戏都是这个形状，**而它们恰好也是 `PrintWindow` 抓不到的那一批**——两条读取路同时断在同一批应用上。
所以**像素必须是主路，不是兜底**。

- 工具：`scripts/uia_tree_dump.cs` / `scripts/uia_tree_dump.py`（只读，不改产品代码）
- 结论文档：`docs/research/2026-08-04-what-uia-actually-exposes.md`
- 提交：`b5b1c74`

## 2. 修掉的真 bug（都有实机复现，不是推断）

### 2.1 "非空 ≠ 读到了"——结构层读回容器身份，就把像素兜底关掉了

**根因**：UIA 的 `uia:region-elements` 对控制台/聊天窗返回的是**容器的可访问名**，实测就是字符串
`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`。它非空 → `structured_succeeded` 判成功
→ `source_kind` 成了 `native_selection` → OCR 富化的两道门（`source_kind` 必须是 `screen_region`、
`content` 必须为空）双双关死 → **OCR 从不运行**。

而同一张截图事后单跑 OCR，53 个块里**精确命中划线那一块**。像素一直都在。

**修法**：新增纯策略模块，判据从"字符串是否非空"改成"**这段文字是不是你划的那一块**"。
三种未命中各有名字，写进 perception trace 和快照：
`identity_only`（读回的是应用自己的名字/exe 路径）、`mark_crossed_no_element`（笔画落在元素间空隙）、
`container_not_selection`（命中的元素比半个窗口还高）。

**同一次还修掉**：笔画穿过覆盖整窗的容器元素时，代码把"穿过了"当成"选中了"，把 1175×30 的
下划线扩成 2346×1142 的整窗选区。

- `app/grounding/marked_read.py`（纯策略）、`tests/marked_read_test.py`、`tests/marked_read_wiring_test.py`
- 提交：`efff10b`

### 2.2 像素路死掉的两种方式（这条是"微信第二次突然就没有结果"的真根因）

**(a) 标题一变就掐断截图。** 守护截图的校验把窗口**标题和 bbox** 也当成身份的一部分。可标题一直在变——
微信来条消息就变，终端跑个命令就变。一变就判 `target_mismatch` → 截图被掐死 → 没有像素 → 什么都读不到。
用户看到的就是「截图目标已变化，未保存或外发图像；请重新指向后重试」。

现场证据：本会话自己的终端标题里有**每帧都在转的动画字符** `⠐`，修之前它必然失败。

修法：身份只看 hwnd + 进程 + 虚拟桌面。**窗口挪了就去它现在的位置再拍一次**，只有一直动不停才加
`geometry_unstable` 备注——**但仍然给截图，不再拒绝**。原有 4 条安全测试改的全是 hwnd/desktop_id，
一条都没被削弱。

**(b) 死帧被当成活帧。** `ImageGrab.grab(window=hwnd)` 走的是 PrintWindow，**它不合成硬件渲染的窗口**——
微信那块 `MMUIRenderSubWindowHW`，"HW" 就是 hardware。返回的是一整块纯深灰（RGB 42），而"空白检测"
只认纯黑（≤2），于是死帧被当成活的，OCR 读到 0 个块，用户什么也没有。

判据改成"整窗毫无明暗变化即抓取失败"。**同一个微信窗口、同一笔划线：OCR 从 0 个块变成 160 个块。**

- `scripts/selection_snapshot_bridge.py`、`tests/window_identity_test.py`、`tests/capture_blank_test.py`
- 提交：`31f25d1`

### 2.3 提问被"锁定对象"这类感知步骤劫持

在真微信上划一条会话问「这是什么」，回的是 `点选元素追问：已锁定 1 个对象，provider=internal`。
L2 把每条能力当工具交给模型挑，它挑了 `element.pick`——这条的 `outputKind` 是 `grounded_object`，
和早就被排除的 `ground.this` 一模一样，只是漏在了手工维护的名单外。

修法：**按 recipe 自己声明的 `outputKind` 判定**，不再靠人记得改名单。

- `app/fabric/intent_router.py`、`tests/non_destination_recipe_test.py`
- 提交：`b7a995c`

### 2.4 回答里不再为自己的感知栈道歉

每个回答都要免责一遍（"UIA 取词失败、这是 OCR 近似"），是因为我们在上下文里**明确要求**模型这么做——
`app/adapters/base.py` 里写着"把 OCR 文本当作近似的视觉观察，不是应用真值"。它只是照办。
用户原话：「这种屁话就别说了哈。没意义。」

现在改成"直接回答，不要描述文字是怎么读到的"。来源全部留在回执、perception trace 和诊断页。
另外：**有内容时**读取过程中的失败不再作为散文交给模型；**什么都没读到时**仍然交给它，否则它会假装看得见。

- 提交：`db8f89b`

### 2.5 「连不上模型端点」其实是网关慢 + 我们预算太短

用户怀疑是本机代理（梯子）没走通。**不是，而且恰恰相反**：同一请求走代理 20.6–26.1 秒，
直连反而更慢 27.3–33.5 秒（httpx 默认 `trust_env`，一直在走 `127.0.0.1:7897`）。

真根因是**生成量**：`max_tokens=1200` 时这个网关真的写满 1198 token 要 26.9 秒，降到 120 只要 12.1 秒。
**上限就是延迟。** 而交互预算 25 秒、Electron 侧 30 秒就杀进程——一个能用的端点被报成不可达。

修法：`ask_text_model` 加 `max_tokens` 参数（气泡用 700）、`GENERAL_TIMEOUT_S` 25→40、
Electron 侧 `selection_bridge` 截止 30s→60s（**截止时间不能短于它要容纳的预算**）、原位改写那条补上有界超时。

- 提交：`6b9f296`

## 3. 模型网关配置（**注意：key 不在版本库里**）

端点换成用户提供的 `https://api.nghimmo.com`，凭据在 **gitignored 的 `secrets/`**：

- `secrets/openai_key.txt` / `secrets/openai_base_url.txt`（`https://api.nghimmo.com/v1`）/ `secrets/model.txt`（`nghi/claude-opus-4.8`）
- 旧值留了 `.bak`。已用 `git grep` 确认 key 与主机名**都没有进入任何被跟踪的文件**。

实测（三条都在真机跑通）：

- 这个网关**两种协议都支持**：Anthropic `/v1/messages` 和 OpenAI `/v1/chat/completions`，所以 `app/ai_client.py` 那套 OpenAI 客户端**不用改**。
- 文本、视觉（`image_url` data URL）、tool calling 全部可用（tool calling 是 L2 路由的依赖，专门验过）。
- 模型别名 `nghi/claude-opus-4.8` 有效，但**回包里的 model 字段永远是 `claude-opus-5`**，不要据此判断实际模型。
- 网关每次请求前塞约 **2.6k token 自有系统提示**（2 token 的输入被算成 2580），且**频繁 429/503**。断路器会正确开路 30 秒。**做端到端验收时必须预留重试**，别把网关抖动当成代码 bug。

### 几个值得单独看的设计判断

- **微信视觉框选的阈值是量出来的**：同一条会话内两行间距 −4~0px，相邻两条会话之间 44~56px。
  第一版写的 1.1 会把 5 条会话并成 1 个，实测后收到 **0.55**。原则是"宁可少合并"——多框一块会
  悄悄扩大后续动作的作用范围。
- **悬浮翻译最危险的失败不是翻不出来，是把第 3 句的译文盖在第 5 句上**。模型少给一行、加句开场白、
  或自己重新编号，都会造成全体错位，屏幕上留下一个看起来毫无破绽的错译。所以**按编号配对**，
  认领不到的槽位空着不覆盖。
- **点选之前只高亮、不改变命令作用范围**，等于高亮是个请求并不兑现的承诺。
- **MCP client 三条铁律**都有真实子进程测试：别人的 server 卡死不能带走这条命令；
  **发现 ≠ 调用**（叫 `delete_everything` 的工具不能因为"看看有哪些工具"就被执行）；
  第三方不能把模型上下文塞满。
- **剪贴板历史**：查是只读的（有测试专门钉"回看历史不能顺手改掉此刻剪贴板"），
  记录点只有一个——**readback 确认复制真的落地之后**，所以失败的复制不会被记成发生过。
- **记忆层不存截图**（有测试会在出现 `capture_path`/`.png` 时失败）。滚动录屏是另一个产品、
  另一场知情同意，而回答"那篇论文叫什么"用不着它。

### 还剩两项，以及为什么没做

- **#5 选中动作条**、**#6 clicky 指针陪伴**。两件都需要**常驻的文本选中监听**——要在没有会话时
  就在后台观察，是个新的常驻组件，不是现有链路的延伸；仓库里目前没有 selection-hook 集成。
  没有硬做，因为半个常驻组件比没有更糟。

  首次约 4.4s（要跑 OCR），之后约 0.7s（命中缓存）。

## 8. 一句话总结

这一轮把"划线读不到内容"这个反复出现、每次都被误诊的问题**测清楚了根因并修掉**：
不是 DPI、不是 OCR 没装、不是超时，而是**结构层读回容器身份被当成读到了**，加上**像素路在
同一批应用上也是断的**。顺带把 P3 十二项做完十项，并给出了用户点名的"证明拿到了"的可视反馈。
剩下两项需要新的常驻组件，已说明原因而不是含糊带过。
