## 二、20 张静态演示图片的共同语言

### 演示 1—6：对象优先、短命令和源—目标关系

`演示1.png` 的关键不是三个建议按钮本身，而是视觉层级：被选中的图片拥有最强的发光边界，命令入口贴着图片右下边缘，输入条里保留对象缩略图，建议动作只用 `Visualize Together`、`Compare items`、`Synthesize` 这类可执行短语。产品名、应用名、字数、适配器和长摘录都不存在。`演示2.png` 进一步说明选择可以跨窗口形成一组引用对象，真正的生成进度进入独立且更合适的 Google 结果窗口，而不是让鼠标旁的小控件变成聊天记录。

`演示3.png` 的 `Merge these` 把两块表格区域视为可组合对象；命令条贴在表格单元格附近，目标是直接改变宿主文档结构。`演示4.png`、`演示5.png` 分别用 `Add this` 和 `Double that` 展示源对象、目标对象和代词：指针命中的食材行是 `this`，右侧购物清单是隐含目的地；第一次添加后，第二次在目标清单中的 `1lb Spaghetti` 上发出 `Double that`，说明代词必须指向冻结后的具体实体而不是一段截图。`演示6.png` 则证明光带只是一段非常短的对象锁定反馈，宿主页面始终是主界面，选区和指针附近不该长期漂浮大面板。

### 演示 11—20：语义对象、直接写回和跨应用行动

`演示11.png` 把网页配方的一项逐个添加到桌面便签，说明用户关心的是“把我指的这一项同步过去”，而不是让模型解释网页。`演示12—16` 来自更完整的原型：系统能识别 `text_notes_841`、`text_notes_529` 等实体 ID；悬停条与输入条视觉上分层；文字逐字飞入命令框；模型生成的代码可替换文本、改正式语气、为清单逐项添加 emoji；结果落回原文本对象。这里虽然出现了比 Google 正式演示更重的开发者面板，但它揭示了底层必需能力：对象 ID、读值、写值、变更脚本/计划、执行历史、对象状态校验，以及把 `this` 解析成当前悬停实体。

`演示17.png` 从海报自动提取活动名称、日期、时间和地点，直接填入日历表单；这不是“读图问答”，而是视觉实体到结构化动作卡的转换。`演示18.png` 用 `make this orange` 直接修改被指文本的样式，表明写动作不只替换内容，还要支持属性级更新。`演示19.png` 把两处地点组合成地图路线，要求跨对象提取地址、去歧义和目标应用调用。`演示20.png` 把一张鸟图的风格迁移到菜单图，体现跨对象生成与新资产写回。20 张图片共同要求的不是一个全能聊天窗，而是一套对象运行时：每次只让用户指出对象和极短意图，系统负责补齐当前应用、结构、目的地、权限、进度与结果归属。

## 三、四段视频逐帧拆解

### 视频 7：食谱到购物清单的连续指代与结构化搬运（不少于 1000 字）

`演示7.webm` 时长 17.875 秒、2950×1908、24 fps。2 fps 接触表清楚显示，它不是一次命令完成全部事情，而是四个连续、极短的小回合。第一回合中，普通黑色系统鼠标移动到食谱的 `1 lb Spaghetti`；对象文字先出现横向淡蓝高亮，鼠标短暂变为蓝色 Magic Pointer，旁边从一个近圆形等待态横向展开成单行胶囊，文字逐步形成 `Add this`。控件高度接近一行文本，左边是很小的聆听/处理图标，胶囊始终与当前行保持一小段间距，不覆盖复选框，也不遮住被命中的文字。动作结束后，右侧购物清单立即出现 `1lb Spaghetti`，胶囊收缩并消失，鼠标恢复普通形态。视觉上没有“打开面板”“发送”“查看答案”这些模式切换，结果本身就是确认。

第二回合中用户移动到 `2oz of Parmigiano Reggiano`，同样的高亮和胶囊复用，但短语是 `and this`。这个 `and` 非常重要：它说明当前任务会话没有在第一次动作后立即遗忘，系统记得正在向同一个购物清单累积食材，也记得上一个动作的谓词是 add。用户不需要重复说“add this to the shopping list”。第三回合不再命中源食材，而是移动到购物清单的空白/列表尾部，短语变成 `here`，这把一个空间位置冻结为 destination。执行后，右侧清单出现之前两项，且带有短暂的蓝色占位/加载条，表明系统是在目标容器里原位写入，而不是先展示一张回答卡。第四回合命中右侧清单里的 `1lb Spaghetti`，短语 `Double that` 直接表达变换；结果变成 `2lb Spaghetti`。`that` 指向刚刚明确的目标对象，`Double` 则是结构化数值变换，不是字符串随便替换。

底层上，这个体验至少需要五层。第一层是对象解析：从浏览器 DOM、UIA 或宿主 API 得到列表行、复选框、文本、数量、单位和容器 ID，而不只是截图框。第二层是连续任务图：`source ingredient -> pending set -> destination list -> created list item`，每个节点带 session token、宿主窗口、位置、文本哈希和有效期。第三层是短语解析器，把 `Add this`、`and this`、`here`、`Double that` 转成 typed operation，并把 this/that/here 解析到冻结对象。第四层是写入适配器：如果目标是网页，就优先用 DOM/可访问性编辑或浏览器扩展；如果目标是原生应用，就用 UIA ValuePattern/TextPattern 或专用 API；所有写入都应验证目标内容。第五层是原位反馈：rail 只显示 listening/recognizing/running/success/error，真正结果由目标宿主展示。

我们的实现不会直接照搬其可能被剪短的速度。为做得更好，必须在用户首次停留目标后 80—120 ms 内出现仅有光圈的预激活反馈，300 ms 内出现 rail 外壳；语音转写或动作推理超过 600 ms 时，rail 仍保持稳定且显示非阻塞波形，不让布局跳动。每个写动作都要预判是否会覆盖、重复或单位冲突；`Double that` 应解析数量与单位，无法确认就只显示拟执行值或要求一次轻量确认。连续会话应允许撤回上一步、取消当前集合、切换目的地，并在用户点击别处、按 Esc、切换前台窗口或超过 TTL 时彻底失效。验收不能只截图：要测从第一次移动到写入完成的总耗时、重复添加率、目标错误率、剪贴板是否变化、宿主焦点是否保留、200% DPI 下是否遮挡复选框，以及连做四步时用户是否需要重新描述上下文。

### 视频 8：图像内对象移动、生成与局部编辑（不少于 1000 字）

`演示8.webm` 时长 18.875 秒、2950×1908、24 fps。它在一张沙滩插画里完成三类动作：搬动已有对象、改变已有对象外观、在指定位置生成新对象。开始时用户把指针移动到右下方戴海盗帽的螃蟹，蓝色指针和胶囊从 `M` 逐字扩展为 `Move this`；随后用户移动到右侧沙洲，胶囊续写为 `to here`。这里的源和目标都不是文本选择，而是图像中的视觉实例与空间坐标。执行阶段没有弹出独立图片编辑器，螃蟹先在原位置消失，目标区域出现短暂像素化/扩散过渡，再在右岸稳定出现。这个过渡同时承担三件事：告诉用户正在处理、掩盖生成延迟、让用户知道结果落在哪里。它比固定 spinner 更贴近对象，但也可能掩盖几秒真实延迟，因此我们的版本必须显示可取消状态并保留原图快照。

第二段用户命中左侧雪人，短语从 `Make` 扩展成 `Make this a sun hat and ...`。最终雪人的红色毡帽变成宽檐彩色遮阳帽，周围有短暂粒子。语义上这不是整图生成，而是局部对象属性替换：主体、姿态、光照和背景应保持不变。第三段用户命中棕榈树顶部附近，短语是 `put a bird here`；执行后目标位置先像素化，再生成一只色彩与插画风格一致的巨嘴鸟。这个回合说明 `here` 必须既包含全局屏幕坐标，也包含局部图像坐标和所在视觉层；如果用户滚动、缩放或窗口移动，目标仍要随图像变换而更新，不能把旧屏幕坐标当真。

底层实现应区分“可编辑画布”和“任意屏幕截图”。在支持的网页/设计应用中，优先读取 DOM/canvas 节点、图层和变换矩阵；在普通图片查看器里，先生成不可破坏的编辑副本，再用视觉分割模型得到对象 mask、深度/遮挡关系和局部坐标。`Move this to here` 可先尝试 cut-and-paste 加背景修补；质量不足再走区域生成。`Make this a sun hat` 是 mask 约束的局部 inpainting，必须锁住未编辑区域哈希或用结构相似度验证背景漂移。`put a bird here` 是目标框与风格条件联合生成，风格条件可以来自当前图像的局部特征而不是上传整张私人屏幕。每次编辑产生 revision ID、原图引用、mask、prompt、seed、输出资产和可逆操作；结果不能直接覆盖用户原文件。

视觉体验要比演示更透明：rail 在识别源对象后可用一条细轮廓或低透明 mask 明确“this”，用户移动到目标时显示小型落点十字或幽灵预览；系统不确定对象边界时允许滚轮/键盘扩大或缩小选择，而不是默默圈错。执行期间原对象不应突然消失到用户以为丢失，可用 150 ms 的 ghost 保留和目标占位；超过 1.5 秒显示阶段化状态“提取对象 / 修补背景 / 融合结果”，并提供取消。生成完成先以可撤销预览层出现，用户继续操作即接受，Esc 恢复。验收要测对象边缘污染、背景漂移、风格一致性、目标偏移、缩放后锚点、取消恢复、连续编辑历史，以及低端 GPU 或远端模型慢时 rail 是否仍稳定、鼠标是否仍能正常操作宿主。

### 视频 9：文档多区域合并与就地语气改写（不少于 1000 字）

`演示9.webm` 时长 15.333 秒、2954×1910、24 fps。视频第一段从一张包含段落和人物表格的文档开始。用户先在表格第一行的多个单元格之间移动/圈选，指针经过区域留下短暂蓝色轨迹和局部高亮，胶囊逐字形成 `Merge these`。执行后表格结构改变：被选中的若干列内容合并到新的 `Persona details` 列，原先 Demographics 等列被重排或清空，最终表格仍保持可编辑结构。这不是把截图交给模型总结，而是识别表格行列、选择多个非连续范围、生成结构化变更计划并通过文档 API 改写。若只能得到像素，系统最多应给出建议，不能冒充已经可靠理解了表格。

第二段用户把指针移动到正文句子，胶囊形成 `Make this more human`，结果原句被改得更自然；第三段命中另一句，短语 `Make this softer`，结果语气变温和。视频里 rail 只在当前句子边缘出现，执行后立即消失；原生文档没有切换到“AI 编辑模式”，也没有长回答。真正重要的是对象粒度会随意图变化：`Merge these` 需要多选表格单元格/列，`Make this more human` 需要精确句子范围，`Make this softer` 可能只改一句而不能重写整段。系统必须同时保留文档结构和文本 range 身份。

底层应以宿主语义为主。对于 Word/WPS，使用 COM Range、表格 Cell/Row/Column、文档 identity、range start/end 和文本哈希；对于网页编辑器，使用 DOM Range、表格节点和编辑事务；对于 PDF，只允许只读理解，不能假装能直接结构化写回。多区域选择应建立 SelectionGroup，记录每个成员的对象 ID、空间顺序、角色和来源，`these` 只解析到当前 group。动作规划先产生可审计 diff：例如把第 1、2 列合并为 `Persona details`，逐行用换行或标点组合，再删除/隐藏原列。文本改写则生成 replacement proposal，执行前再次验证原文、范围和宿主窗口，写后读取确认并记录撤销锚点。当前项目已有 Word 单选区安全替换与撤销，这能成为基础，但表格结构、WPS 隔离和浏览器编辑器事务仍缺失。

做得更好意味着把“模型会写”升级为“用户始终知道改哪里、改什么”。rail 在语音/输入尚未完成时不显示三个通用按钮；识别出 `Merge these` 后，可以在 rail 左侧显示极简的 `3 cells` 或三段叠层图标，但不重复全文。高风险结构变更先显示一行 diff 摘要，如“3 列 → 1 列，保留 2 行”，用户点击或停顿确认后执行；普通语气改写可以预览新句并让 Enter 接受、Esc 放弃。结果直接在文档中以宿主修订/临时高亮呈现，rail 只显示勾号或失败原因。必须测试重复文本、表格合并单元格、受保护文档、协作编辑导致 range 漂移、旧模型结果覆盖新选区、撤销只撤自己的动作、中文/英文标点、200% DPI 和长文档滚动后的锚定。

### 视频 10：从视频语义到真实预约动作卡（不少于 1000 字）

`演示10.webm` 时长 18.208 秒、2952×1908、24 fps。用户在网页内播放“Top 10 Places to Eat in Tokyo”的视频，把指针移动到视频画面中一家店铺的招牌附近，蓝色光带标出当前指向的视觉实体，胶囊逐字形成 `Book a table here tomorrow`。这里 `here` 不是光标坐标本身，而是视频当前帧里被指店铺；`tomorrow` 是相对日期；“book a table”需要从内容理解跃迁到外部执行。命令提交后 rail 变成 `Processing...`，随后右侧展开一张轻量卡：先显示 `Saraku Shibuya` 与 4.9 评分，再扩展人数、日期和时间选择；用户点选 8:00pm，卡片收回为一条状态条，显示确认中、环形进度，最后变成蓝色勾选完成。整个流程始终贴着视频右侧，不打开另一个聊天应用，也没有让用户重新输入餐厅名称。

这段视频最容易被误读成“模型看到店名然后自动订位”。真实实现必须拆成可验证步骤。首先是时序视觉 grounding：冻结视频 URL、播放器、时间戳、当前帧、指针坐标和目标区域，通过 OCR/VLM/字幕/页面元数据识别候选店铺。其次是实体解析与消歧：店名、城市、地址、评分和来源要与网页附近标题或搜索结果交叉验证，低置信度时让用户在 rail 内选择候选，而不是自动订错。第三是动作提供方：优先使用餐厅官网、地图/预订平台 API 或浏览器自动化，并明确哪些字段已经确定、哪些需要用户选择。第四是结构化表单：人数、日期、时间、时区、可用性、价格/押金、取消政策与登录状态必须独立建模。第五是提交边界：查可用时段可以自动执行，真正下单、产生费用或发送个人信息前必须明确确认；执行后保存确认号和来源链接，而不是只显示一个勾。

视觉上，演示的渐进披露非常好：最初 rail 只有一句话；当系统需要输入时才扩成对应动作卡；完成后又收回一行。这是“同一任务的阶段视图”，不是聊天卡膨胀。我们的版本应进一步把风险和可取消性做清楚：`Processing` 超过 800 ms 就显示当前阶段；候选店名出现时允许一键纠正；人数与日期使用键盘可达控件；时间段加载失败时保留前一步；需要登录时打开来源页面并把任务会话挂起，而不是吞掉状态；最终确认条应包含店名、日期、时间、人数和“打开确认”入口。所有外部动作要有幂等键，避免重试造成重复预约。

验收需要真实任务沙盒，而不是只播放动画：用固定测试网页和模拟预订 API 验证视频暂停/播放时目标不漂移、店名 OCR 错误能被发现、跨时区 tomorrow 正确、无可用时段有清晰降级、用户取消不发送请求、网络超时可重试、重复点击不会重复下单、提交前必须确认、完成后有可验证回执。性能上，目标实体冻结后 300 ms 内出现 rail，候选识别 1.5 秒内给出第一结果；更慢时必须显示阶段并允许用户继续看视频。真正“比演示更好”的标准不是更炫，而是任何一次订位都可解释、可校正、可取消、可验证。

## 四、缺失的真实体验功能：用户愿望与预期实现

以下十项不是随意列出的 feature backlog，而是把当前代码、20 张图片和四段视频之间的差距按用户能感知的完整体验分组。每一项都用“如果我是用户，我希望……”的口径描述，并同时约束视觉、交互、底层、失败处理和验收。

### 愿望 1：我希望指到一个东西时，只出现真正的一行操作条，而不是任何形式的迷你聊天卡（不少于 1000 字）

如果我是用户，我希望 Magic Pointer 的第一反应像鼠标能力自然增强，而不是又打开一个应用。我已经用系统鼠标选中了文字、停在图片、表格行或按钮上，界面就不应该重复告诉我“THIS 是 PDF 选区、43 字、来自 Edge、文件叫某某”。这些信息对调试有用，对我没有用。我希望对象本身始终是视觉主角：原生蓝色高亮继续保留，鼠标旁只出现 36—48 DIP 高的一条 rail，宽度随当前短命令变化。最短时它可以只是一个 36 DIP 的聆听圆点；识别到意图后向不遮挡对象的一侧横向展开，例如“解释这一段”“加到清单”“放到这里”。它没有产品标题、关闭栏、来源摘要、多个并排通用按钮，也不在初始态显示答案。按 Esc、继续滚动、点击宿主其他位置或切换窗口时，它应立即消失，我不需要先找关闭按钮。

这条 rail 应该有明确而克制的状态机：`hidden -> sensing -> composing -> ready -> running -> success/error -> hidden`。每个状态仍然保持一行，不允许通过向下扩张解决复杂度。`sensing` 只显示短时圆形脉冲和对象边缘反馈；`composing` 显示实时语音转写或键入文本；`ready` 是可执行短语；`running` 保持同宽或小幅扩展，展示不跳动的进度；`success` 用 400—800 ms 的勾号和结果摘要确认后收起；`error` 用一句可行动的原因，如“目标已变化，重新指一下”，而不是堆栈或通用“失败”。长解释、代码和多选表单不能塞进 rail，而应在动作执行后进入独立次级 surface，或者直接落到宿主应用。

视觉实现上，rail 使用透明 Electron `BrowserWindow` 或未来的原生轻窗，背景轻微半透明但保持高对比度；圆角与演示接近胶囊，不要玻璃拟态大阴影。其宽度根据文本测量得到，设置最小 44、理想内容宽度、最大约 360 DIP；超过最大值保持单行省略并允许用户主动展开次级视图。rail 与指针热点、选区 union rect、屏幕工作区和其他候选控件保持可测试的 gap。位置算法应复用现有 `computePanelPlacement` 的 DPI、多显示器、负坐标和 overlap 逻辑，但输入尺寸改成动态宽高；优先放在对象右侧，其次下、上、左，绝不覆盖原生高亮、复选框、输入 caret 或候选目标。显示必须使用 `showInactive()`，不改变前景 HWND；只有用户明确点击/键盘进入输入时才请求焦点，并在完成后归还宿主。

底层上，rail 不能自己拥有业务真相。它只消费 `SelectionSession` 的 `token + summary + geometry + onePrimaryIntent`，通过事件发送 typed command，运行状态由 action runtime 回推。当前 `panel.js` 的 `capture-summary`、三个 `suggestion-chip`、`bubble-expand` 和结果区应从初始路径剥离；安全 Markdown 与 action preview 可以保留给次级 surface。现有未提交 V4 的 `showInactive()`、session token 校验和位置测试可以继续用，但 `bubble/expanded` 命名应被 `inline/secondary` 取代。第一版可以在没有语音时显示一条自由输入 rail，或根据选区类型只给一个高置信建议；不能因为模型不确定就塞回三个按钮。

验收必须同时包含 DOM/静态、位置、焦点和真实桌面测试：初始 HTML 不得出现产品标题、来源元数据和多个 suggestion；窗口高度不超过 48 DIP；宽度会随 4、12、30 个字符变化；100%/200% DPI、右边缘、任务栏、负坐标副屏均不遮选区；触发前后 `GetForegroundWindow()` 不变；剪贴板序列号不变；新选区出现时旧 rail 与旧结果失效；真实截图与演示 1、演示 7 并排时，一眼看上去属于同一交互类别。最重要的人因指标是：解释一个选区或添加一项时，从唤起到完成的可见操作不多于一次短命令和一次确认，并且普通用户不会把它叫作“弹窗”“卡片”或“聊天框”。

### 愿望 2：我希望唤起动作自然、可靠、几乎不误触，而且系统在我还没开口前就已经悄悄准备好对象（不少于 1000 字）

如果我是用户，我希望 Magic Pointer 既能像演示那样通过轻微晃动或停留被唤起，也不能在我正常移动鼠标、玩游戏、画图或快速扫网页时到处冒泡。我需要至少三种入口并保持同一行为：全局热键作为最可靠的明确入口；可配置的 wiggle 作为熟练用户入口；指针停留加按键/鼠标侧键作为低误触入口。语音不能作为唯一开关，因为办公室、会议、夜间和无麦克风环境都不合适。无论用哪种入口，系统都必须先冻结对象、再显示 rail，不能先抢焦点再回头猜刚才指的是什么。

自然唤起应分成“预热”和“承诺”两阶段。预热可以在指针速度降低、停留于可操作对象 120—250 ms 后，在后台只读查询当前前台窗口、UIA/DOM 对象和几何，不显示任何大界面，也不调用昂贵模型；它建立一个极短的候选快照并把常用 adapter 热起来。用户真正 wiggle、按热键、侧键或开始说话时，系统用最新候选与实时前景 HWND 做一致性校验，100 ms 左右给出蓝色光圈，随后才建立正式 SelectionSession。这样冷路径不会每次都先启动 C# 探针、Python 和模型。预热数据不写日志、不上传、不跨窗口保留，超时后丢弃。

wiggle 检测不能只看左右反转次数。它需要在 250—600 ms 窗口内综合横向速度、方向反转、垂直漂移、总位移、回到中心的程度和当前应用类型，并设置冷却时间。绘图、表格拖动、游戏、视频剪辑等应用默认禁用或提高阈值；鼠标按键按下、滚轮快速滚动、窗口拖动时不触发；连续误触后自动降低敏感度并在设置里给出原因。第一次启用应让用户选择“仅热键 / 热键+晃动 / 侧键”，并提供 10 秒校准，而不是偷偷监听。系统应记录本地匿名的触发原因、是否立即取消、是否完成动作，用取消率调整阈值，但不记录用户内容。

视觉反馈必须区分预热、已锁定和正在听。预热完全不可见或只在指针内出现极淡的单帧变化；正式锁定才显示 150—250 ms 的外扩光圈，且光圈围绕真实系统指针，不绘制第二只鼠标。当前项目已有 observer aura 和 click-through overlay，可以复用，但 overlay 不应覆盖全屏接管点击，也不能把 trail 变成永久装饰。激活失败时，例如当前窗口不支持、没有选区或对象仍在变化，只显示短句“再停一下”或“先选中内容”，800 ms 后消失，不弹面板。

底层建议把触发器统一为 `ActivationIntent`：包含 source、timestamp、foreground HWND/PID、cursor、velocity history、button state 和 desired input mode。`beginSelectionSession()` 只接受已经过验证的 ActivationIntent；预热层维护 adapter cache 与候选 object fingerprint，正式捕获层重新读前景句柄并 fail closed。Office、UIA、浏览器扩展和视觉 grounding 都实现统一 `probeCandidate()`/`freezeObject()` 接口，避免 Electron 主进程继续增长。为控制延迟，C# UIA helper 常驻或采用命名管道，Python PDF 恢复仅在 UIA 与可见高亮边界冲突时启动，文本模型在 rail 已经显示后异步工作。

验收要用真实鼠标轨迹而不是手写单元测试：采集正常浏览、快速扫动、拖拽、圈选、画图、窗口移动、游戏式摆动和有意 wiggle 各至少 100 段，测 precision、recall、立即 Esc 率和唤起延迟。日用目标可以先定为每小时误触少于 0.1 次、有意 wiggle 成功率大于 95%、P50 光圈反馈低于 120 ms、P95 rail 外壳低于 350 ms。触发前后宿主焦点、剪贴板、鼠标捕获和滚动行为必须完全不变；当机器忙或 adapter 冷启动时，也要先给可取消反馈，不能让用户晃第二次造成重复 session。

### 愿望 3：我希望可以自然地说“这个、那个、这些、这里”，系统连续几步都不会忘记或指错（不少于 1000 字）

如果我是用户，我希望 Magic Pointer 最独特的价值不是给单个选区做总结，而是让我用人类本来就会的指代完成连续任务。比如我先指配方里的面条说“加这个”，再指奶酪说“还有这个”，再指右侧清单说“放这里”，最后指刚生成的面条项说“把那个翻倍”。我不想每一步重述应用、文件、清单名称和完整文本，也不想打开对象历史抽屉。系统必须知道 `this` 是当前命中对象，`that` 是上一轮被明确引用或新生成的对象，`these` 是当前显式集合，`here` 是当前目的地/插入位置；这些代词的解析要可见、可过期、可纠正，而不是模型凭聊天上下文猜。

实现上需要从当前单个 SelectionSession 升级为短时 `InteractionEpisode`。episode 里保存有向对象图：每个节点是 ObjectSnapshot，包含 adapter、宿主、稳定 ID、屏幕几何、内容摘要/哈希、能力和版本；每条边表示 `selected-after`、`added-to`、`created-from`、`destination-of` 等关系。`THIS` 在每次新 grounding 后更新；`THAT` 不是简单取数组上一项，而是取上一轮语义焦点或动作结果；`GROUP` 只包含用户在当前 episode 中显式累积的对象；`HERE` 是带容器和局部坐标的 DestinationAnchor。episode 在前台应用切换、长时间停顿或明确完成后不一定立即销毁，但涉及写入的引用必须在使用前重新验证。

用户界面不应展示开发者式对象列表。对象被加入 group 时，可以在原对象边缘闪一下编号或在 rail 左侧叠一枚小缩略/数量，例如 `2 items`；`here` 被锁定时目标容器出现短时落点线或插入 caret。若系统把 `that` 解析错，用户可以把指针移回正确对象并说“不是这个，是那个”，episode 应重绑定而不丢掉已经选好的其他对象。Esc 第一次取消当前 rail，连续 Esc 或“清空这些”才清空 group。用户切换任务时，旧 episode 安静过期，不出现全局历史污染。

底层最关键的是身份稳定性。DOM 对象使用页面/框架/节点路径加语义属性和内容哈希，Office 使用文档 identity、range/表格 cell 与邻接锚点，图片对象使用原图 revision、mask 与局部坐标，普通 UIA 对象使用 runtime ID、automation ID、control type、name 和顶层 HWND。所有对象都要有 `resolveLive()`，动作执行前确认它仍对应原实体；如果页面重排、列表项重新渲染或文档被协作编辑，系统用多证据重定位，歧义则请求用户重新指，不擅自选第一个。DestinationAnchor 还要记录插入规则：追加、替换、放在某项之后、画布坐标或表单字段。

指代解析器应先用确定性规则再用模型。命令文本中的 `this/that/these/here/它/这些/这里/刚才那个` 映射到 episode 槽位；谓词决定需要的类型，例如 `merge these` 要求集合，`put this here` 要求源与目的地，`double that` 要求可数值化对象。槽位缺失、能力不匹配或对象版本过期时，rail 只提出最小澄清，如“要放到哪？”并进入等待 here 状态；不能让大模型偷偷补目标。

验收应覆盖至少二十种连续序列：源—源—目标、目标先于源、选择后滚动、跨窗口、对象被删除、页面刷新、相同文本重复出现、目标容器排序、生成结果成为 that、撤销后继续、episode 超时和用户纠正。每一步都检查 token、对象 identity、宿主焦点和实际写入位置。核心指标是连续四步成功率与重述次数：理想情况下用户只说视频 7 那四个短语就完成任务；系统一旦不确定，宁愿停在一行澄清，也不能把错误写进看似合理的目标。

### 愿望 4：我希望“放到这里”真的能跨应用写入正确位置，而且任何高风险动作都可确认、可验证、可撤销（不少于 1000 字）

如果我是用户，我希望把网页的一条食材放进便签、把海报信息放进日历、把一段内容放进 Word、把地址放进地图时，Magic Pointer 能理解目标的结构，而不是只把文本复制到剪贴板然后让我自己粘贴。我希望目标位置可以通过指一下、选中一个字段、放置 caret 或显式标记来确定；系统执行后，结果直接出现在那个宿主里。如果目标已经变化、不可编辑、登录失效或存在歧义，系统必须在写之前停下来。我还希望撤销只撤 Magic Pointer 刚做的那一步，不影响我随后手工编辑的内容。

现有工程的 Word replacement 已经建立了正确底线：typed proposal、显式确认、文档/range/hash 校验、写后读取验证、历史记录与锚点撤销。下一步应把它抽象为统一 `DestinationAdapter` 协议，而不是为每个功能写脚本。协议至少包含 `inspectCapabilities(snapshot)`、`prepare(operation)`、`preview(diff)`、`commit(plan, idempotencyKey)`、`verify(expected)` 和 `undo(receipt)`。每个写入计划包含源对象、目标对象、动作类型、变更范围、预期前后状态、风险等级、是否需要确认、幂等键和过期时间。读与写严格分离：UIA 只读适配器不能因为模型生成了文本就自动升级成写能力。

浏览器目标可分三层实现。第一层是受控本地浏览器扩展/Native Messaging，获取当前 tab、DOM Range、可编辑元素、框架和 mutation 版本，并通过 input/beforeinput 事件或站点适配器写入；第二层是 UI Automation 的 ValuePattern/TextPattern，仅支持可证明的标准输入控件；第三层才是鼠标/键盘自动化，而且只能在用户明确确认、窗口与元素完全绑定、可验证回读时使用。微信、聊天软件和 Electron 应用也要按 UIA 能力逐个白名单接入，不能用 `Ctrl+V` 泛化一切。Office 继续用 COM/WPS API；日历、地图和预订优先使用 API 或 deep link。

视觉确认要按风险渐进。把一条无敏感信息追加到用户已经指明的本地清单，可以在 rail 内显示“添加 1 项”并让 Enter 确认，或在用户开启“低风险直接执行”后写入再提供撤销。替换文档、发送消息、创建日历事件、预订、付费、删除和对外发布必须显示清晰的目标与关键字段；确认 surface 可以是动作专用小卡，但必须在用户真正进入高风险步骤后出现，不能污染初始 rail。执行期间目标宿主显示临时高亮/占位，完成后 rail 给出 receipt；失败时明确是“目标变化”“权限不足”“网络失败”还是“验证不一致”。

撤销模型要基于执行回执而不是“最近一次操作”。receipt 保存 adapter、宿主 identity、修改前后摘要/哈希、稳定范围、外部服务 id、时间和 undo strategy。Word 用 range/锚点；DOM 用 transaction 与节点版本；表单追加可删除由本次创建的特定节点；日历/预约用服务端事件 ID；生成图像用 revision。若用户已经在结果上继续编辑，系统不得强行覆盖回旧状态，而应显示冲突并提供可审阅的恢复方案。

验收用真实沙盒应用做矩阵：Word/WPS、Edge contenteditable、普通 input、网页表格、日历测试账号、地图 deep link、模拟预约 API、微信只读/草稿路径。必须测试相同文本、多窗口同名文档、协作编辑、页面重载、iframe、权限拒绝、网络重复提交、确认后目标改变、写后回读不一致和撤销冲突。所有外部写动作都检查幂等性与审计，任何一次无法证明写到正确对象的情况都 fail closed。用户体验指标不是“支持多少应用”，而是承诺支持的路径目标错误率接近零，失败也不破坏用户数据。

### 愿望 5：我希望鼠标指到的东西不局限于文字，图片、表格、文件、视频帧、按钮和画布对象都能被准确理解（不少于 1000 字）

如果我是用户，我希望 Magic Pointer 的“这个”真正覆盖桌面上的实体：选中的文字、网页卡片、表格单元格、文件资源管理器项目、图片里的物体、视频当前帧的店铺、日历字段、地图地点、设计画布图层。我不应该知道 DOM、UIA、OCR、COM 或模型之间的区别；但系统也不能为了显得万能，把任何鼠标附近的像素都猜成对象。我希望它在能证明对象时直接行动，在证据不足时用最小轮廓告诉我它看到了什么，让我一眼纠正。

底层需要统一的 `GroundedObject` 2.0。当前工程已有 grounding schema、Explorer grounder、Office/UIA adapters 和 PDF 恢复，可以扩展为多证据对象：`identity`、`kind`、`source`、`geometry`、`semanticValue`、`structure`、`capabilities`、`evidence[]`、`confidence`、`version`、`privacyClass`。grounding 管线按可靠性排序：宿主专用 API/DOM/COM > UI Automation 结构 > 文件/页面内语义 > 局部截图 OCR/分割/VLM。高层证据与低层证据不一致时不取平均，而是标记冲突；例如 UIA PDF 文本与高亮边界冲突时，像当前 V3 一样用本地 PDF 字符框验真，无法证明就拒绝。

网页需要浏览器 companion/扩展提供 DOM hit-test、可访问名称、role、文本范围、CSS box、frame、URL 和节点版本；文件资源管理器继续用 Shell/UIA 与路径解析；Office 用 COM Range/Cell/Shape；图片编辑用画布节点或分割 mask；普通截图用窗口边界、OCR、检测和局部 VLM。视频对象必须冻结媒体元素、当前时间、帧图像和局部坐标，并将识别实体与字幕、页面标题、附近文本或搜索结果交叉验证。表格对象要保留行列、表头和合并关系，不能只输出一块文字。按钮/控件要区分可点击能力与只读描述，避免模型把装饰图标当操作。

为了速度，grounding 不能每次把全屏发给大模型。前景窗口变化时建立只读结构缓存；鼠标移动使用轻量 hit-test 更新候选；真正激活时只裁剪对象及少量上下文。模型调用采用分级预算：结构证据足够就不调用 VLM；OCR/局部分割只在视觉对象需要时启动；跨对象生成才发送必要资产。隐私上，每个对象标记数据范围，rail 在即将上传截图或文件内容时给出可理解的来源提示，敏感应用可完全禁用视觉模型。

视觉反馈应与置信度匹配。稳定 DOM/COM 对象用紧贴边界的短时细线；文字沿用宿主原生选择；图像 mask 可显示半透明边缘；只知道粗框时用柔和角标而不是假装精确。若多个候选重叠，用户可轻微移动指针或滚轮切换候选，rail 显示对象名称的极短变化；不要弹出调试树。系统不应该永久改变鼠标样式，锁定时的蓝色指针只持续到对象确认，随后回到系统指针或低干扰状态。

验收要建立对象基准集：浏览器文本/按钮/卡片/iframe/canvas、Word 文本/表格/图片、WPS、Explorer 文件、Edge PDF、聊天输入框、图片内小物体、视频帧实体、不同 DPI 和多显示器。每个样本记录真实对象 ID、边界、语义、能力与不可执行边界，测 top-1 grounding、几何 IoU、身份稳定性、滚动/缩放后的重定位和冲突拒绝率。对于写动作，grounding 置信度门槛要高于只读解释；宁可少支持一个应用，也不能让用户产生“它看懂了”却写错地方的信任崩塌。

### 愿望 6：我希望可以用短语音、键盘或鼠标任选一种表达命令，三种方式都不打断当前工作（不少于 1000 字）

如果我是用户，我希望像演示中的 `Add this`、`here`、`Double that` 一样，用两三个词就能完成动作；但我不希望 Magic Pointer 强迫我在公共场合说话，也不希望每次都先点击输入框再等待焦点。我希望按住鼠标侧键或一个热键就说，松开即完成；安静环境可以直接键入；明显的上下文动作可以点 rail 上唯一的建议。三种输入都写入同一个短命令缓冲、作用于同一个冻结对象、遵守同一确认策略，不因为入口不同而产生三套界面或三种行为。

语音入口应采用 push-to-talk 或 click-to-talk，默认不常听。按下时 rail 从 sensing 进入 listening，左侧图标用稳定波形反馈音量，文本在同一行逐字出现；松开后进入 finalizing，200—500 ms 内稳定最终文本。用户可在识别过程中用键盘修正，Backspace、Esc、Enter 与普通输入一致；识别错误时不需要打开转写历史。连续指代模式允许短句分段，例如先说“加这个”，再移动说“还有这个”，episode 负责补上下文，而不是语音模型保持无限对话。

实现上先复用 Windows 系统听写只适合作为过渡，因为 `Win+H` 会有系统浮层、焦点依赖和语言设置差异。正式版本应抽象 `SpeechProvider`：本地 Windows Speech/Whisper、本地可选模型、云端流式 ASR 都输出统一的 partial/final events、语言、置信度和时间戳。音频只在用户明确按住/点击后采集，默认不落盘；云端传输前显示一次性权限说明和提供方。麦克风设备、输入语言和快捷键在设置里可选；识别失败时立即回退为键盘，不阻断已冻结对象。

短命令理解需要专用轻量层，而不是把每个 partial 都发送给大模型。首先做语种归一和命令 grammar：动词（解释、添加、移动、合并、改写、预订）、代词（this/that/these/here）、参数（时间、数量、语气、语言）和风险词。确定性解析足够时直接生成 typed intent；歧义或开放式改写才调用文本模型。这样 `Double that`、`Add this` 的响应不必等完整大模型。partial 只影响 rail 文本，不产生动作；final 后才建立 plan，防止逐字飞入时误执行。

键盘体验应支持真正的零鼠标切换。热键唤起并冻结对象后，用户直接开始打字即可，rail 接收按键但不让宿主先收到半句；若用户只是想继续宿主输入，Esc 立即归还且不残留字符。可配置“双击 Ctrl”或侧键进入输入，避免抢占普通字母。候选建议不是三个 chips，而是浅色自动补全尾巴；Tab 接受、继续输入覆盖、Enter 执行。鼠标点击唯一建议也复用同一个命令。

视觉上必须控制 rail 的字符飞入效果：演示 12—15 的逐字动画能表明正在识别，但如果每个字母从指针飞过去会干扰阅读且消耗 GPU。我们的版本只在首次锁定时有一段 150 ms 的微光连接，partial 文本以轻微淡入/宽度弹性更新；为了避免抖动，rail 使用预测宽度、固定字符 baseline 和 80—120 ms 的布局节流。长命令超过最大宽度时让文本横向平滑滚动或在末端省略，不能变两行。

验收包括共享办公室、无麦克风、蓝牙断连、中英文混说、口音、噪声、说一半取消、partial 回滚、键盘与语音同时修改、宿主快捷键冲突和输入法组合态。指标不仅是 WER，还包括端到端意图准确率、P50/P95 首字延迟、松开到 final 延迟、误激活录音次数和用户纠正成本。任何录音都要有明确可见状态；窗口隐藏、锁屏、权限撤销或用户松开后立即停止采集，不能出现“它是不是还在听”的隐私疑虑。

### 愿望 7：我希望动作执行时看得懂进度，失败时知道该怎么办，成功后能在原处确认并随时撤销（不少于 1000 字）

如果我是用户，我希望 rail 的“快”不是把几秒等待藏掉。我发出一个动作后，应马上知道系统已经接住命令、当前在做什么、是否还可以取消。简单本地动作 300 ms 内完成时，用一次轻微进度和勾号即可；复杂图像生成、PDF 恢复、预订或跨应用写入超过 800 ms 时，rail 应显示阶段化短状态，例如“识别目标”“准备修改”“等待确认”“写入并核对”，但始终一行。真正结果在宿主里出现后，rail 只保留短确认与撤销入口，几秒后收起。我不希望看见通用 `Processing...` 无限转圈，也不希望失败只说“Something went wrong”。

底层需要统一 `OperationLifecycle`，把现在分散在 bridge、action proposal、renderer result 中的状态收束成有序事件：`accepted`、`grounding`、`planning`、`awaiting_confirmation`、`executing`、`verifying`、`succeeded`、`failed`、`cancelled`、`rolled_back`。每个事件带 operation ID、selection episode、adapter、进度语义、可取消标记、用户可读消息和调试详情引用。renderer 只显示用户可读短消息；完整日志写本地但不包含不必要的敏感正文。旧 operation 的事件必须受 token/nonce 保护，不能覆盖新对象 rail。

取消不是简单杀进程。只读模型请求可中止；浏览器/Office 写入在 commit 前可取消；已提交外部请求要根据幂等键查询状态，再决定撤销或标记未知；图像生成可停止等待但保留服务端结果隔离；预订必须在用户确认后仍处理网络超时的“可能已成功”状态，不能盲目重发。所有 adapter 都声明 cancellation semantics 和 rollback support。用户按 Esc 时，rail 首先取消当前未提交动作；如果动作已经不可逆，显示一句“已提交，正在确认状态”，而不是假装取消成功。

成功反馈要与动作结果建立因果连接。写入文本后目标 range 闪一次低干扰绿色边线；添加列表项后新条目短时高亮；移动图片后新位置出现 ghost-to-solid；创建日历事件后卡片显示标题与时间；预约返回服务端确认号。rail 的勾号只在 `verify()` 通过后出现，不以 HTTP 200 或进程退出作为成功。验证失败时，如果可以安全自动回滚，就回滚并说明；无法回滚则保留冲突状态和打开详情入口。

失败信息按用户能采取的下一步分类：目标丢失→“目标变了，重新指一下”；权限不足→“该应用暂不允许写入，可复制草稿”；网络失败→“未提交，可重试”；验证冲突→“结果不一致，已保留原内容”；模型不确定→“我不确定指的是哪一项”。技术堆栈、异常类和 adapter 名称放进诊断文件，不出现在 rail。重试复用同一 operation 幂等键或明确生成新操作，避免重复写入。

撤销入口应是时间有限但可靠的。成功后 rail 可在勾号旁显示 2—4 秒的回退箭头；rail 消失后，托盘的“最近一次 Magic Pointer 操作”仍可撤销，但必须绑定 receipt。现有 Word 历史与锚点机制可泛化到 DOM transaction、图片 revision、日历 event ID 和预订 cancellation link。若用户手工修改结果，撤销先检测冲突并展示差异，不能为了实现按钮而破坏后续工作。

验收使用故障注入：模型超时、Python/C# helper 崩溃、UIA 返回空、前景切换、DOM 重渲染、网络半断、服务端超时但实际成功、写后回读不同、用户中途 Esc、重复 Enter、旧响应迟到。每种情况必须落到唯一终态，不悬挂、不重复执行、不把失败当成功。体验指标包括首次反馈延迟、无解释 spinner 的最长时间、取消生效率、错误可恢复率和误报成功率；后者必须接近零。

### 愿望 8：我希望在确实需要时得到专用动作卡，而不是万能聊天面板；日历、地图、预约、比较都用各自最少的字段完成（不少于 1000 字）

如果我是用户，我希望大多数动作只用一行 rail，但当任务真的需要补参数时，系统能够渐进展开一张与任务匹配的动作卡。例如海报到日历只问缺失的日期/时间，视频预约只问人数和时段，地图路线只让我确认两个地点，商品比较只展示我关心的三项差异。动作卡不是默认首页，也不是对话记录；它在系统已经理解对象和意图之后出现，完成或取消后收回 rail，不留下悬浮工作台。

实现上需要 `ActionCardSchema`，而不是让模型直接生成 HTML。schema 定义 card type、title、source receipts、fields、validation、confirmation copy、submit action、risk、loading states 和 completion receipt。首批可做四类：CalendarEventCard（标题、开始/结束、地点、时区、提醒）、RouteCard（起点、终点、方式、出发时间）、ReservationCard（实体、人数、日期、时段、费用/政策）、CompareCard（对象集合、比较维度、证据来源）。模型只填结构化候选值和置信度，renderer 使用本地可信组件；未知字段保持空并明确要求用户补齐。

动作卡的出现位置仍与对象相关，但尺寸可以超过 rail。它应优先占用对象旁空白区或屏幕边缘，不遮住源证据；必要时变成可停靠的侧片，但不抢宿主全屏。打开时 rail 作为卡片标题/锚点，动画从一行渐进展开；关闭后回到同一 rail 或完全消失。卡片的输入控件支持键盘、屏幕阅读器和高 DPI，不能像视频里的营销原型只靠小圆点。任何外部费用、发送或创建都在底部有清晰动词按钮，不使用模糊“继续”。

海报到日历的流程需要 OCR/视觉提取标题、日期、时间和地点，结合本地时区解析相对日期；重复活动要检测；提交前显示将写入哪个日历。地图路线需要把两个 GroundedObject 解析成地点候选，保留来源文本和地理编码置信度；若“Paris”之类歧义就让用户选。预约卡在查可用时段前可自动请求，真正订位前确认人数、时间、取消政策和账号。比较卡要引用对象证据，不能用模型幻觉填规格；点击一项可回到来源对象。

底层 connector 与 adapter 分离。Calendar/Maps/ReservationProvider 都实现 discover、preview、commit、verify、undo/cancel；本地默认使用 deep link 或用户已有浏览器会话，未来可接 API。凭据不写进项目 secrets 明文，权限按 provider 管理。动作卡本身没有执行权，只提交 typed plan 给统一 executor。操作带 idempotency key，服务端回执进入 ActionReceipt。

与聊天相比，动作卡最大的优势是限制自由度。模型不能在预约卡里任意加字段，renderer 不能执行未注册 action；字段 validation 与时区/金额格式由本地代码负责。长解释可以放 secondary reader，不混进 action card。若 provider 不可用，卡片可生成草稿并给“在浏览器打开”或“复制已结构化内容”，不假装完成。

验收为每类卡建立固定 fixture 和模拟服务：缺字段、歧义地点、跨午夜、夏令时、重复日历事件、无可用时段、费用确认、登录过期、服务端重试、取消政策变化和完成后撤销。UI 测试验证从 rail 到 card 再回 rail 的焦点顺序、选区不被遮挡、Esc 行为、键盘可达和屏幕阅读器名称。最终指标是用户补的字段比手工打开应用更少、错误提交率低，并且任何一张卡都能清楚回答“将对哪个对象做什么”。

### 愿望 9：我希望长解释、生成内容和操作历史有安静的次级空间，需要时看，不需要时完全不挡住对象（不少于 1000 字）

如果我是用户，我希望“解释这段”可以得到完整且可读的答案，但这个答案不应该让对象旁的一行 rail 膨胀成 380 DIP 的聊天卡。我希望短结果直接显示在 rail 或宿主，长结果进入一个明确的次级阅读层：可以是屏幕边缘的小侧片、跟随当前任务的阅读器、或写入我指定的文档。它默认不出现历史对话，不把此前几十个对象缩略图都塞进上下文；我可以关闭它继续工作，重新打开时仍知道答案对应哪个对象。

次级 surface 应与 inline rail 在窗口和代码层分离。rail renderer 只处理短状态与命令；`SecondaryReaderWindow` 负责 Markdown、代码、引用、图片、diff 和 action card，并拥有独立尺寸、拖拽/停靠、滚动和可访问性。它接收 immutable `ResultArtifact`：artifact 包含来源 session、对象指纹、prompt/intent、模型/本地处理来源、正文、引用、创建时间和可用后续动作。rail 点击“查看”或长结果自动完成后，可在不抢宿主焦点的情况下显示侧片；用户明确点击后才聚焦。

阅读器不能变成无限聊天。默认只显示当前 artifact 和少量与当前 episode 直接相关的结果；需要追问时使用当前对象/结果作为新 intent，旧记录折叠。历史以操作/结果为单位而非消息流，支持“打开来源对象”“复制结果”“写入目的地”“固定到任务”“删除本地记录”（产品最终应支持用户删除，但当前项目开发阶段遵循不删除工作区文件的约束）。敏感内容默认只本地保存摘要或由用户配置不保存。

解释类结果应提供证据边界。PDF/网页答案显示引用到选中范围或本地页面；文件理解标出文件名与页码；视觉结果显示裁剪来源；模型不确定明确说明。生成代码或写作结果在阅读器中只作为草稿，点击应用才进入 typed proposal 与确认。比较结果可以用专用表格，但来源对象可点击回到原窗口/位置。

视觉风格要与 rail 统一但层级不同：rail 是瞬时胶囊，reader 是稳定阅读 surface。reader 可以 320—480 DIP 宽，贴边而不是贴指针，不覆盖当前选区；用户拖动后记住位置。加载长内容时使用骨架/流式排版但避免段落跳动；代码块和表格内部滚动；关闭 reader 不取消后台已经完成的 artifact。多显示器时 reader 留在触发对象所在屏或用户固定屏。

底层结果存储应从现在的对象 JSONL/动作历史中分离出 artifact store，保留 schema 版本和内容策略。episode 只引用 artifact ID，不把全文塞进 Electron IPC；大图片/文件通过本地路径和权限读取。模型请求的上下文由当前对象、显式 group、destination 和必要 artifact 构成，不默认加载全局历史。这样既减少 token，也避免旧任务污染 `this/that`。

验收包括 1 行、10 段、长代码、表格、图片、多语言、流式中断、模型失败、来源窗口关闭、切换显示器和重新打开 artifact。rail 在任何长结果下都不得超过 48 DIP；reader 显示/隐藏不改变宿主前景，除非用户点击；历史不能让新 session 误指旧对象。用户研究要比较“解释后继续原任务”的时间与传统聊天跳转，目标是查看答案后一次点击或 Esc 即回到原对象。

### 愿望 10：我希望它像一个可以每天信任的 Windows 产品：安装简单、设置清楚、隐私可控、性能稳定、无障碍可用（不少于 1000 字）

如果我是用户，我希望 Magic Pointer 不是只能从源码和终端启动的演示。我希望下载一个可信安装包，首次启动用 2—3 分钟完成快捷键、wiggle、麦克风、模型和隐私设置；托盘图标明确显示运行/暂停；应用更新不破坏设置；异常后能恢复；我随时知道它何时观察、何时上传、何时写入。它不应该要求我阅读 adapter、session 或 API key 文档，也不应该在 README 里出现乱码和过时的“鼠标框选截图”主流程。

产品化首先要统一运行架构。当前同时存在 846 行 Tkinter `app/main.py`、672 行 Electron `main.js`、612 行 overlay 和多种 bridge，容易产生两个前端、两套状态与僵尸进程。应确定 Electron 为主要 shell，Python/C# helper 作为受管服务；逐步把触发、session、operation lifecycle、window management 分成独立模块，保留旧 Tkinter 仅作迁移或诊断而不并行常驻。打包使用 electron-builder/MSIX 或等价方案，签名、自动更新、开机启动都可选。helper 随包发布，首次运行不临时编译 C#；依赖版本固定，日志与缓存有明确目录和配额。

设置中心至少包括：激活方式与快捷键、wiggle 灵敏度/禁用应用、语音设备与语言、模型提供方与本地/云端选择、允许读取/写入的应用、低风险动作是否自动执行、日志/历史保留、截图/文件是否可上传、外观和无障碍。权限采用“默认最小”：只读、写入、发送/创建/付费分级；第一次使用某项能力时解释为什么需要，而不是一次索取所有权限。敏感应用名单可快速暂停；托盘提供“暂停 15 分钟”“仅热键”“完全退出”。

隐私可见性要贯穿体验。只读 UIA/DOM 本地处理无需每次打扰，但即将把截图、文件正文或音频发到云端时，rail/动作卡显示简短云图标并允许取消。日志默认不保存完整私人文本，只保存哈希、类型、耗时和错误；诊断包由用户主动生成并可预览。API key 使用 Windows Credential Manager/DPAPI，不放在工作区 `secrets` 明文。远端模型与本地模型的能力差异要说明，离线时基础 grounding、Office 本地动作和历史仍可用。

性能目标应成为产品承诺：常驻内存、CPU 和 GPU 在空闲时接近零；鼠标监听不造成卡顿；P50 光圈 <120 ms、rail <350 ms、常见本地动作 <800 ms；冷启动也先有即时反馈。adapter helper 常驻但按需唤醒，模型预热受电源/隐私设置控制。故障隔离要保证某个 Python/C# helper 崩溃不会带走 shell，watchdog 可重启且不重复动作。日志有 correlation ID，崩溃后恢复未完成 operation 为明确未知/失败，不假装成功。

无障碍和国际化不是最后补丁。rail、动作卡和 reader 支持键盘完整操作、屏幕阅读器名称、200%/300% 缩放、高对比主题、减少动画、色盲安全状态、左右书写方向与中英文输入法。指针光圈不能只用颜色表达锁定；听障用户不依赖声音；运动敏感用户可关粒子/轨迹。多显示器、负坐标、任务栏位置和远程桌面都要测试。

发布验收包括干净 Windows 机器安装/卸载/升级、无管理员权限、首次引导、断网、本地模型、代理异常、休眠唤醒、屏幕锁定、DPI 切换、多用户会话、崩溃恢复、日志隐私扫描和无障碍审计。只有当普通用户不打开终端也能启动、暂停、理解权限、完成一次安全动作并撤销，才可以称为产品，而不是代码仓库中的实验。

## 五、方案比较与本轮选择

### 方案 A：继续修补现有 V4 气泡

优点是改动小，session、建议按钮、结果区都已接通。缺点是交互类别错误：即使再压缩，它仍以摘要与多个 action 为中心，无法满足一行、对象第一、动作后消失的硬要求。此方案不采用。

### 方案 B：在现有安全底座上重做独立 inline rail（采用）

保留 selection snapshot、`showInactive()`、DPI/多屏位置、stale token、typed action 与安全写回；把初始 renderer 收敛为单行状态机，动态宽度，单一主意图，不显示元数据与长结果。长内容和动作卡暂时留在后续独立 surface。本方案既能最大化继承已验证底座，又能真正改变前台交互类别，是本轮推荐方案。

### 方案 C：直接引入完整 UFO/UI-TARS/浏览器代理重写

优点是长远覆盖面广，可能复用规划和 UI 自动化。缺点是会扩大不确定性、延迟和误写面，且当前最明确缺口只是 rail 体验。它们可作为 adapter/测试参考，但本轮不进入运行时。

## 六、首个实施切片：Inline Action Rail V1

### 目标

在不破坏 `3f0299a` 的选区读取、安全会话和写回机制的前提下，将被否决的 V4 初始气泡替换为演示 1/7 同类别的一行 rail。第一版只支持一个主意图、键盘短命令、已有 suggestion 的单一选择和状态反馈；不在同一窗口显示长结果，不新增语音、DOM 写回或多对象执行。

### 文件边界

- `electron/renderer/panel.html`：只保留一行 rail 的语义结构；初始路径不包含标题、capture summary、三按钮区或多行输入。
- `electron/renderer/panel.css`：定义 36—48 DIP 高、动态宽、单行、省略、状态动画和减少动画模式。
- `electron/renderer/panel.js`：实现 rail 状态机、单一主 suggestion、短命令输入、token/nonce 防迟到；长结果只发出 secondary 请求或暂时给短完成提示。
- `electron/main.js`：将窗口默认高度改为 44 DIP，动态宽高 resize，继续 `showInactive()` 与 session 绑定；不改变捕获与 action bridge。
- `electron/panel_position.js`：若现有接口不能支持动态宽度，只做最小扩展；继续复用候选位置与 overlap 计算。
- `tests/panel_static_test.js`：先写失败断言，禁止标题/摘要/多建议，要求 rail 状态与单行 DOM。
- `tests/panel_position_test.js`：先写动态宽 44 DIP 高、边缘、负坐标和选区零重叠用例。

### V1 状态与交互

1. 热键冻结选区后，rail 以非激活窗口出现，显示唯一高置信短意图；若没有建议，显示“输入短命令”占位。
2. 用户点击或使用键盘进入输入时，rail 仍保持一行，文本横向增长，Enter 提交、Esc 关闭。
3. suggestion 只取第一项，不同时摆出解释/总结/翻译；更多动作留给后续明确入口。
4. 提交后 rail 显示一行 running；短结果/成功/失败仍是一行。现有长结果暂不在 rail 渲染，后续由 secondary reader 承接。
5. rail 高度上限 48 DIP，宽度 88—360 DIP 动态变化；位置不覆盖 selection rect，前台 HWND 与剪贴板保持不变。

### 本轮不做

- 不实现语音 ASR。
- 不实现 THIS/THAT/HERE 多对象写入。
- 不新增浏览器扩展、日历或预约 connector。
- 不重构全部 600—800 行大文件。
- 不提交或删除 `2307.00583v1.pdf`。
- 不删除任何文件或运行会删除 PID 文件的停止脚本。

- `git diff --check` 无错误，删除审计为空。
